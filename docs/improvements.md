# 基盤の改善の提案

2026-10-16、LLM デッキの 7 章を 8 本作り直したあと、ボスに聞かれて Claude が挙げた改善の案です。作業で実際につまずいた所と、同じ手間をくり返した所から挙げました。どれも、まだ手を付けていない提案です。数字は、この日の作業で測ったものです。

作り方は、5〜7 章と同じでした。編集役のセッションが章の筋、原稿、裏取りを先に作り、クリップは 1 本ずつ別のサブエージェントが作ります。1 本あたり 40〜60 分、ツール呼び出し 120〜160 回、50〜65 万トークンかかりました。

## すぐ効く、小さな改善

1. **作業の道具と引き継ぎ書を、リポジトリに入れる。**
   - いまの状態: 次の道具は、どれもジョブの一時フォルダ（`~/.claude/jobs/<job>/tmp/`）にしかない。
     - 字幕の行数を数える `sublines.mjs`
     - o200k_base でトークンに切る `tok/tk.mjs`
     - 画素を比べる `pngdiff.py`
     - クリップの長さの一覧を出す `durations.mjs`
   - 困ること: サブエージェントに毎回読ませている引き継ぎ書（`brief.md`）と、編集役の進行メモも、同じ場所にある。ジョブを消せば、全部なくなる。
   - 改善: 道具は `tools/` に移す。`npm run check -- <deck> <id>` 一つで、字幕の行数、「の。」の並び、長さ、読みの注意をまとめて出せるようにする。引き継ぎ書は `docs/` に置く。
2. **公開の送信量を半分にする。**
   - いまの状態: 反映するたびに約 52MB を送っている。2026-10-16 のイメージの層は、`COPY /app/dist`（35.8MB）のすぐあとの `RUN chmod -R a+rX /app` が、同じ 35.8MB をもう一層丸ごと作っていた（`docker history` で確かめた）。
   - 改善: 権限を build の段で整えてから COPY すれば、この重複は消える。音声を別の層に分ければ、コードだけ直した反映は数 MB で済むはず。
   - ボスの判断が要る点: AGENTS.md に「`chmod -R a+rX /app` を消さない」とある。消すのではなく build の段へ移す変更なので、ボスの承認を受けてから行う。
3. **画素の比べを、手作業から e2e へ移す。**
   - いまの状態: 共通の部品（`lib/harness.js` など）を足すたびに、サブエージェントが、前のクリップの止まりの絵を、足す前と後で撮り比べていた。7-7 では 213 枚だった。
   - 改善: 止まりの絵のハッシュを e2e に持たせ、意図して変えたときだけ更新するコマンドを置く。そうすれば、毎回の確認がいらなくなる。

## 作業の流れで出ていた無駄

4. **原稿が三か所にある。**
   - いまの流れ: README の第 1 稿と、裏取りで直した文の表から、編集役が手で「いまの文」を組み立てていた（7 章では一時フォルダの `ch7-current.md`）。サブエージェントは、それをクリップの `script` に写していた。
   - 改善: 「台本先行」にする。
     1. 第 1 稿を、絵のないクリップの雛形の `script` に直接書く。合成の前でも、見積もりの長さで無音のまま再生できる。
     2. 裏取りは `script.md` を読む。
     3. 直しは、その場で入れる。
   - 効果: README には理由だけを残し、直しの表は差分から作れる。
5. **デッキの README が長すぎる。**
   - いまの状態: LLM デッキの README は 3,587 行ある。サブエージェントは毎回、4 章の段から自分の章の段まで読む。1 本あたりのトークンが多いのは、読む量の多さも効いている。
   - 改善: 章ごとの制作メモ（`decks/llm/notes/ch7.md` など）に分け、README はデッキの狙い、構成、事実と出典に絞る。
6. **重なりとはみ出しを、機械で見つける。**
   - いまの状態: 各クリップの直しの多くは「札が枠に触れていた」「字が重なった」の類で、止まりの絵を目で見て一つずつ探していた。
   - 改善: `src/kit` の文字や箱を描く関数に、描いた矩形を記録させ、静止点で重なりと舞台の外を一覧にする。`place()` と `ringBox()` の延長で作れる。
7. **読みを、合成の前に確かめる。**
   - いまの状態: 7 章では、次のような読み違いを、合成のあとのカナで見つけていた。
     - 年が三つの句に割れる
     - 「12 本」「4-5」「#128」「Opus 4」が、二つの句に割れたり、違う読みになったりする
   - 改善: 数字と助数詞、ハイフンでつないだ番号、# の付いた番号などの型を、合成の前に警告する。あわせて、「4-5」のようなクリップの番号の言い方を、デッキで一つに決めておく。

## 共通化できる所（作る自由は残したまま）

8. **つなぎの「写し」をやめる。**
   - いまの状態: どのクリップも、前のクリップの最後の絵を、自分の頭で描き直している。`lib/harness.js` は 3,099 行、232 個の export になり、その多くは `final74`〜`final77`、`G73`、`TOOL76` のような、クリップごとの置き換え。
   - 改善: 部品を名前の付いた層（文書、画面、ツールの場所、カード）として描かせる。エンジンに「前のクリップの終わりの層」を渡させれば、渡りでは、どの層を片づけ、どの層を動かすかを書くだけで済む。
9. **エージェントの図を、出来事の並びで書く。**
   - いまの状態: 5〜7 章の 19 本は、同じ出来事をくり返し描いている。文書に項目を足す、LLM がトークンを書く、ハーネスが止めてツールを動かす、結果が戻る、文書を上へ送る、の連なり。クリップごとに 500〜1,000 行の手続きになっている。
   - 改善: `doc.append(...)`、`llm.write(tokens)`、`harness.run(tool)` のような出来事を声の印に結びつけて並べ、動きは部品が作る。特別な絵は、これまでどおり自由に描けるよう、逃げ道を残す。

## 根本的な改善

10. **保持型のステージ（名前の付いた要素の集まり）。**
    - 考え方: いまはクリップを「時刻から絵を描く関数」として書いている。これを「時刻から、名前の付いた要素の状態を返す関数」にする。時刻の純粋関数であることは保てる。
    - 効果:
      - クリップのつなぎ（現れる、消える、動く）を、エンジンが自動で作れる。
      - 重なりの検査も、止まりの比べも、要素の数字で行える。
      - 撮影は、PNG と一緒に要素の座標の JSON を出せる。作る側は、絵を目で読む代わりに数字で確かめられる。
    - 導入のしかた: 書き直しは大きいので、次のデッキ（高校数学、[next-deck.md](next-deck.md)）から使い始めるのが現実的。
11. **章の「物語」をデータにする。**
    - 考え方: 7 章の通しの例（依頼、呼び出し、結果、要約、報告）を、章に一つのデータとして持つ。各クリップは、その一部を窓として見せる。
    - 効果: 例の中身がクリップごとにずれることがなくなり、文書の送りや量の帯も、データから決まる。
12. **編集役とサブエージェントの手順を、道具にする。**
    - いまの手作業: 編集役が毎回手で回しているのは、次の手順。
      1. 引き継ぎ書と、クリップごとの頼み文を書く。
      2. 止まりの絵を見る。
      3. 直しを頼む。
      4. 進行メモを付ける。
    - 改善: これをリポジトリの中のスキル（または codexctl の manager の型）にして、進行の状態もリポジトリに置く。そうすれば、どのセッションからでも続きを始められる。

## 進める順の案

1（道具と引き継ぎ書をリポジトリへ）、2（送信量。ボスの承認が要る）、3 と 6（止まりの絵の自動比べと、重なりの検査）の順を勧める。3 と 6 は、8〜10 の土台にもなる。エンジンと道具の実装は、分担の決まり（[AGENTS.md](../AGENTS.md) の「分担」）どおり codex（GPT-6 Astra）に向く。
