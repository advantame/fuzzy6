# 引き継ぎ書: 語りつきのクリップを 1 本作る

編集役のセッションが、クリップを 1 本ずつサブエージェントに任せるときに、最初に読ませる文書です。2026-10-15〜16 に LLM デッキの 5〜7 章を作ったときの引き継ぎ書（ジョブの一時フォルダにあった `brief.md`）を、どのデッキにも使える形に直して、2026-10-17 にリポジトリへ移しました（[improvements.md](improvements.md) の 1）。

編集役は、この文書に加えて、その仕事だけの指示（作業ツリー、クリップの id、章の段、手本のクリップ、裏取りの報告）を渡します。章ごとの決まりは、デッキの README の章の段に書きます。

## あなたの仕事

あなたは、ウェブアプリ「Motion Explorer」（fuzzy6）のデッキで、語りつきのクリップを **1 本だけ** 作ります。章の筋と原稿の第 1 稿は、編集役がもう決めてあります。あなたが受け持つのは、その原稿をもとに、絵と動きを描き、声を合成し、撮って見て直し、確かめて、コミットするところまでです。終わったら、編集役に報告を返します。

人間の指示者は「ボス」と呼びます（「ユーザー」は、デッキを見る人とアプリの利用者のことです）。

## 作業の場所

- 作業ツリーとブランチは、編集役が指示します。すべてのコマンドはそこで実行します。`~/projects/fuzzy6`（`main` の作業ツリー）には触れません。
- dev サーバは、その作業ツリーから起こします（`npm run dev` は port 5175）。ほかの作業ツリーが 5175 を使っているときは、編集役の指示する port で起こし、道具には `FUZZY6_URL=http://127.0.0.1:<port>` を付けます。ほかの dev サーバは止めません。
- 一時ファイルは、編集役が指示する一時フォルダに置きます。リポジトリの中に一時ファイルを残しません。

## まず読むもの（この順に）

1. `AGENTS.md` の全部。とくに「表現の決まり」「クリップを作る手順」「気づいたこと」。書いてある決まりは、すべて守ります。
2. `docs/spec.md` の §5.1（歩調）、§6.6〜§6.10（原稿、時間割、止まり、つなぎ）、§7.1〜§7.3（語りの記録、配役、語彙）。
3. `docs/narration.md`（VOICEVOX に読ませる書き方）。
4. デッキの README の、編集役が指す段。「見た目の文法」と、あなたの章の段（原稿、絵の方針、裏取りで直した文）。
5. 手本のクリップと、デッキの共通の部品（`lib/`）。編集役が指します。
6. あなたのクリップの前の版があれば、それも読みます。使える材料（トークンの切れ目、JSON など）があります。
7. 同じ章で先に仕上がったクリップ。配置と部品は、それにそろえます。

保持型のステージ（[stage.md](stage.md)）で書くかどうかは、編集役が決めます。保持型で書くときは、前のクリップの最後の絵を写さずに、`from` で受け取ります。

## ボスが直したこと（やりがちな誤り → 直し方）

LLM デッキの 3〜7 章で、ボスが直したことです。

- **決まりとして説明してしまう** → 作る側から語る。「これはアプリの仕事」ではなく、「アプリに〜させるの」。困ること（このままだと〜してしまう）を先に絵で見せ、手当てを後に出し、「確かに、これでうまくいく」と思える文を置く。
- **印が「付く」、答えが「出る」と言ってしまう** → だれが書き、だれが読んで動くかを、文と動きの両方で示す（LLM デッキの紫の外枠と墨の外枠のように、書き手を色で分ける）。
- **声に対応する絵の変化がない文** → どの文にも、声の印（`{name}`）の時刻に起きる絵の変化を付ける。地は文の頭で出し切り、答えは声が来たときに出す。動きの一覧で、絵の変わらない文を探す。
- **抽象的すぎて、何が起きているのかが見えない** → 具体的に動かす。最初の数回はゆっくり見せる。困ることは、実際に起きたように見せると伝わる。
- **その場で作った言い換え** → 用語で呼ぶ。中身を見せてから「〜を、…と呼ぶ」と名前を付け、そのあとは用語で呼ぶ。
- **何を言っているのか不明瞭な文** → 一文で一つの関係を言い切る。図で指せないことは言わない。
- **静止点の絵が散らかる** → 静止点は、絵が一枚の図版として読める時刻にだけ置く。そこでは強調を解く。
- **字幕が 3 行に折れる** → 1 行は全角 35 字まで（立ち絵を出すクリップでは、実際に収まるのは 29 字ほど）、2 行まで。`\n` を自分で入れる。一枚に収まらない文は、空行で字幕を何枚かに分ける（spec §6.6）。
- **読み違い** → 合成のあとに出る読み（カナ）を、全文で見る。数字、英語、記号、かぎ括弧の前後。直し方は `docs/narration.md`。
- **「の。」を続ける** → 同じ話者の隣り合う二文を「の。」で終えない（unit テストが落ちる）。「の」を「わ」に置き換えて済ませず、文ごと直す。
- **だれが、だれに、何をするかがわからない** → 「頼み」のような語を使わず、する側と相手を書く。字幕の字数に合わせて言葉を削らない。
- **共通の部品を直して、ほかのクリップの絵を変えてしまう** → 部品を足すときは新しい関数として足し、いまある配置の関数は変えない。直したら `npm run stops` で、ほかのクリップの止まりの絵が変わっていないことを確かめる。
- **札を、薄くした要素の上に重ねる** → 札は、薄くした要素の字にもかけない。
- **終わった絵に、途中の札が残る** → 最後の絵では、終わった形にする（「調べています」ではなく「調べました」）。

## 描き方の約束

- クリップは時刻の純粋関数（spec §6.1）。乱数は `src/kit` の `hash` / `mulberry32`。
- 時刻は `at('印')`、`at('文.end')` などと `pace` から求める。クリップの頭からの秒を数字で書かない。動きのための秒は、文の `lead`、`tail`、`rest` と、印からのずれだけ。
- 強調の語彙は四つ（朱にする、少し持ち上げる、ほかを薄くする、囲む）。`src/kit/cue.js` の `focus`、`ring`、`ringBox`、`enter`。量を表す図形は、強調のために伸び縮みさせない。
- 図に添える文字の位置は `src/kit/place.js` の `place()` と `placeAround()` で決め、強調の枠は描いた関数が返す箱を囲む。手で測らない。
- 例の数値や出力には「例」の札。事実には出典を小さく添える。トークンの切れ目は、実際のトークナイザで切ったもの（`npm run tok`）。
- 文の間（`rest`）は既定の `'normal'` か `'short'`。`'long'` は、図ができたばかりで見せる時間が要る文だけ。話す速さは基本の 1.3。
- 語りの長さは目安 90 秒、上限 3 分。絵のための待ちで延ばさない。
- 字や部品が重なる、はみ出す、触れる、を許さない。

## 手順

1. 原稿をクリップの `script` に書き、文ごとに地、答え、動きを割り振ってから描く。
2. `npm run narrate -- <deck> <id>` で読み上げの文と効く語彙を見る。`--generate` で合成する。
   - 合成はエンジンを一時起動する（port 8083）。別のセッションが合成中だと止まるので、数分待ってやり直す。既存のプロセスは止めない。
   - 文を外したら、`--prune` で使っていない録りを片づける。
3. `npm run check -- <deck> <id>` で、長さ、字幕の行数、「の。」の並び、読みの注意をまとめて見る。終了コードが 1 なら直す。
4. 撮って見る（画像は `test-output/<deck>/` にできる。Read で開いて見る）。
   - `npm run capture -- <deck> <id> --stops`（止まりごとと、各文の頭から 1 秒後）
   - `npm run capture -- <deck> <id> --sheet --every 0.75`（動きの一覧。速い所は `--every 0.25` や時刻の指定で）
   - `npm run check -- <deck> <id> --overlap --stops`（重なり、枠に触れる字、はみ出しの一覧）
5. 共通の部品を直したら、`npm run stops -- <deck>` で、ほかのクリップの止まりの絵を基準と比べる。あなたのクリップの基準は、絵が決まってから `npm run stops -- <deck> <id> --update` で書き換える。
6. `npm test`、`npm run test:e2e`、`npm run build` を通す。台本（`decks/<id>/script.md`）は dev サーバが書き直す。古ければ `npm run script -- <deck>`。
7. 記録を書く（Markdown は Edit か Write で直す。Bash で書かない）。
   - デッキの README の「構成」の表の、あなたのクリップの行（中身と秒）と、「事実と出典」の表の行。
   - 制作メモの末尾に、日付つきの段。決めたこと、第 1 稿から変えた文と理由（表）、絵で決めたこと、読みで直したもの、録り、長さ、確認。
   - `decks/<id>/voice/README.md` に、足した語りを日付と一緒に書く。
8. コミットする（指示されたブランチのまま）。メッセージは英語の命令形の 1 行の題と、本文に何をしたか。最後の行に `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`。`main` への取り込みと push はしない（編集役がする）。

## 原稿の直し方の範囲

- 字幕の折り返し、読み、声の印の位置のための小さな言い換えは、あなたの判断でしてよい。
- 絵の都合で、文を二つに分ける、短い文を足す、のもよい。そのときは、README の段の表に、第 1 稿の文といまの文と理由を書く。
- 話の筋（何を言うか、どの順で言うか、だれに何を問わせるか）を変えたいときは、変えずに、報告で理由を添えて提案する。
- 編集役が、裏取りで直した文を渡したら、その文を使う。

## してはいけないこと

- sudo、システムの設定、グローバルな install。依存を足さない。
- あなたの担当でないクリップの中身を変える。
- `git push`、`main` への取り込み、公開版への反映。
- `git stash`（ほかのセッションと共有している）。
- 長い確認（`npm run play` など）を走らせている間に、`decks/` や `src/` の `.js` を書き換える（Vite が読み直す）。

## 報告（最後のメッセージに書く）

1. 作ったもの: クリップの id、長さ（秒）、文の数、静止点。
2. 第 1 稿から変えた文と理由。筋について提案があれば、それも。
3. 共通の部品に足したもの（関数の名前と役目）と、`npm run stops` の結果。
4. 確かめたこと: unit / e2e / build の件数と結果、`npm run check` の結果、読みで直したもの。
5. 編集役が見るべき画像のパス（止まりのフォルダ、動きの一覧、気になる時刻の絵）。
6. コミットのハッシュ。
7. 迷ったこと、残っていること。
