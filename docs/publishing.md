## 反映の手順

- 公開版への反映は、このリポジトリのセッションが実行してよい（`SHIP_BWLIMIT_KBPS=2048 bash ~/projects/fuzzy2/platform/scripts/ship-app.sh fuzzy6`。ssh と docker を使うので、サンドボックスの外で実行する）。
- 送信の帯域の上限は、2026-10-16 のボスの指示で、fuzzy6 では 2 MiB/s（`SHIP_BWLIMIT_KBPS=2048`）にした。道具の既定は 256 KiB/s で、道具の注釈には「DGX の上り（約 5Mbps）の半分以下」とある。上限を上げても、回線の速さを超えては送れない。既定そのものは基盤のリポジトリにあり、ほかのアプリにも効くので、変えていない。
- 届くのは、`~/projects/fuzzy6`（`main` の作業ツリー）の HEAD のコミットだけなので、先に `main` へ取り込む。例外は `.shipinclude` に書いた Git 管理外のファイルで、いまは立ち絵の画像（`decks/*/figures/**`）だけ。道具は、これをその作業ツリーからイメージに足す（下の「Git に入れないファイル」）。合成した原本の WAV のような、ほかの Git 管理外のファイルは入らない。作りかけのクリップを `deck.js` に載せたまま反映しない。
- 道具は、コンテナの中と入口経由の `/healthz` まで確かめて、結果を一行で返す。最初の送信は約 74MB で数分かかった。二度目からは、変わった部分だけを送る。
- 2026-10-14、サーバ（ssh の別名 `bio`）への ssh が、IPv4 ではポート 22 でタイムアウトし、IPv6 ではつながった。道具は「サーバーで差分の土台を用意できない（本番は変えていない）」と言って止まる。基盤のリポジトリと `~/.ssh/config` には触れずに、`exec /usr/bin/ssh -6 "$@"` だけの `ssh` をスクラッチの場所に置き、その場所を `PATH` の先頭に足して道具を走らせたら、反映できた（rsync と git の ssh も、同じ `PATH` から引かれる）。IPv4 がつながらない理由は調べていない。続くようなら、運用者に伝える。
- 2026-10-15、3 章と 4 章を作り直した版（`1c95699`）を反映したときも、IPv4 では同じところで止まり、同じ対処で反映できた。送った量は約 54MB で、送信に 5 分ほどかかった。二日続いたので、ボスに伝えた。
- 2026-10-16、7 章を作り直した版（`c38054f`）を反映したときは、IPv4 のポート 22 でそのままつながり、対処なしで反映できた。送った量は約 52MB（53,210 KiB）で、送信に 4 分ほどかかった。
- 2026-10-16、立ち絵を足した版（`31c06f1`）を、`.shipinclude` に対応した道具で反映した。足したファイルは 66 個（3 デッキ × 22、2.3 MB、指紋 `f0cbae4bd496`）。送った量は約 37MB（38,145 KiB）で、対処なしで反映できた。反映の前に、同じ材料から手元で作ったイメージを、基盤と同じ制限で 127.0.0.1:8080 に起動し、3 つのデッキで立ち絵の画像が読み込まれ、rail に「立ち絵:akihiyo」が出ることを、ブラウザで確かめた。

## Git に入れないファイル（.shipinclude）

- **2026-10-16、ボスの決定。** 公開版にも立ち絵を出す。画像は、これまでどおりリポジトリに入れない。リポジトリに上げたくないデータを使うアプリは今後も出そうなので、仕組みは fuzzy6 の中ではなく、基盤の反映の道具（`ship-app.sh`）に足す。基盤のリポジトリの編集は、ふだんは運用者の仕事だが（上の「基盤との分担」）、このときはボスの指示で、このリポジトリのセッションが行った。
- 仕組み: リポジトリの最上位の `.shipinclude`（コミットする）に、パターンを 1 行に一つ書く。道具は、これを HEAD のコミットから読み、パターンに合う「Git が無視していて、追跡もされていない」ファイルを、`main` の作業ツリーからビルドの材料に足す。Git、サーバにあるソースの控え、GitHub には入らない。入るのは、DGX とサーバのイメージだけ。
- 合うファイルが一つも無いパターンがあると、道具は本番に触る前に止まる。立ち絵の無い作業ツリーから反映して、公開版の立ち絵が黙って消えることはない。
- 道具は、足したファイルの個数、大きさ、内容の指紋を一行で出し、イメージのラベル（`fuzzy2.local-files.count` と `fuzzy2.local-files.sha256`）にも残す。サーバで切り戻すと、イメージに入っていた立ち絵ごと戻る。
- `.dockerignore` は、それまで `decks/*/figures/` を除いていた。材料に足しても `docker build` で落ちるので、2026-10-16 にこの行を外した。
- 立ち絵の原本は、この機械にしかない。元の PSD は `~/projects/fuzzy6/staging/` に、書き出した PNG は各作業ツリーの `decks/*/figures/` にある。基盤のバックアップは、アプリのデータのボリュームしか取らない。PNG を失くしたら、`tools/figures/export.py` で書き出し直す（[environment.md](environment.md) の「立ち絵」）。
- 2026-10-16、`main` の作業ツリーの `decks/llm`、`decks/trig`、`decks/anglesum` の `figures/` に、立ち絵を写した。三つの作業ツリーにあった組は、どれも同じ 22 ファイルだった。立ち絵を使うデッキを足したら、`main` の作業ツリーにも画像を置いてから反映する。
- 立ち絵が入ると、rail のクレジットに「立ち絵:akihiyo」が出る（各デッキの `deck.js` の `hasFigures`）。

## イメージとサーバ

- 基盤に載せるイメージは、ルートの `Dockerfile` が作る。ビルドの段で `npm ci` と `npm run build` を走らせ、実行の段には `dist/` と `server/` だけを入れる。
- サーバ（`server/serve.mjs`、`npm start`）は Node の組み込みだけで動く。起動のときに `dist/` を一度だけ読み込んで圧縮し、そのあとはディスクを読まない。読み込む量の上限は 128MiB と 1 万個で、超えると起動しない（2026-10-11 の `dist/` は約 800 個、起動後のメモリは約 36MiB）。
- サーバは基盤の契約に合わせてある。`PORT`（既定 8080）で待ち受け、`/healthz` に 200 を返し、それ以外の要求には、基盤の入口が付けるヘッダー `X-App-User`（`user1` など）を求める。ヘッダーのない要求は 403 になるので、手元でサーバを確かめるときは `curl -H 'X-App-User: user1' …` のように付ける。ブラウザで出来上がりを見るだけなら `npm run preview` を使う。
- イメージを手元で確かめるときは、コミットする内容だけを別の場所へ取り出してビルドし、基盤と同じ制限を付けて起動する（uid 10001、メモリ 1GB、CPU 2、プロセス 512。待ち受けは 127.0.0.1 の 8080）。2026-10-11 にこの形で、契約の各項目と、ブラウザでの表示と音声を確かめた。
- この機械の umask は 077 で、取り出したファイルは持ち主しか読めない。そのままイメージに入ると、別の利用者で動くサーバが自分のファイルを読めず、起動に失敗する（2026-10-11 に実際に起きた）。`Dockerfile` の中で読み取りを付けてある（`chmod -R a+rX /app`）ので、この行を消さない。

## リンクの書き方

- 基盤は、アプリを公開 URL の途中（アプリからは見えない接頭辞の下）に置く。そのため `vite.config.js` の `base` を `'./'` にしてあり、ページどうしのリンクも `decks/llm/` のように相対パスで書く。自分で書く `href` や iframe の `src` を `/` で始めると、公開版で切れる（HTML の `<script src>` のように Vite がビルドで書き換えるものは別）。
