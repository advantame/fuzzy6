## 制作の検査道具（2026-10-17）

[improvements.md](improvements.md) の 1、3、6 を、codex（GPT-6 Astra）が作った。どれもクリップと engine の振る舞いは変えない。`check` と `stops` は dev サーバに頼む。URL の既定は `http://127.0.0.1:5175` で、別の作業ツリーの dev サーバを使うときは `FUZZY6_URL=http://127.0.0.1:8080 npm run check -- llm session` のように渡す。unit の `tests/script-plugin.test.js` は port 8080 で自分のサーバを立てるので、8080 で dev サーバを動かしているときは、unit の前に止める。

- **`npm run check -- <deck> [clipId …]`**: クリップごとに、長さ、文と静止点の数、字幕の一枚ごとの行数、同じ話者の「の。」の並び、録りのカナ、読み違いが起きやすい型（数字と助数詞、ハイフンでつないだ番号、# の付いた番号など）を出す。字幕は、立ち絵の画像があるかどうかによらず、立ち絵を出すときの幅で測る。問題の結果で読む文（spec §6.6 の `when`）も、その結果になる答えを与えて測る。字幕の行数が書いた行数と違うか、隣り合う「の。」があると、終了コードは 1。注意だけなら 0。`--deck` を付けると、本線の章ごとの長さと合計を、深掘りの長さとは分けて出す。
- **`npm run tok -- '文字列' …`**: o200k_base（GPT-4o）で切り、トークンの数と切れ目を出す。js-tiktoken 1.0.21 に固定した。例えば「セッションを手元のファイルに残して」は 11 トークン（`セ | ッション | を | 手 | 元 | の | ファ | イル | に | 残 | して`）。UTF-8 の文字の途中で切れたトークンは、単独では読めない字になるので、ID も添える。
- **`npm run pngdiff -- a.png b.png`**: 二枚の PNG の画素を比べ、違う画素の数と、その範囲の箱を出す。8 bit の RGB と RGBA で、インターレースのないものだけを読む。一致なら終了コード 0、違えば 1、読めない画像は 2。

### 止まりの基準

e2e は、すべてのデッキのすべての止まり（spec §6.8）で、ステージの絵を基準と比べる（`tests/e2e/stops.spec.js`）。共通の部品を直したとき、ほかのクリップの絵が変わっていないかを、手で撮り比べる代わりに確かめる。

- 基準は `tests/stops/<deck>.json` にある。止まりごとに、`001@1.000:line:a`（番号、時刻、種類、文）のような名前と、ステージの画素のハッシュを持つ。深掘りも含み、問題は答えのない状態で撮る。
- 撮り方は、`&clean` で、viewport を 1600 × 900、deviceScaleFactor を 1 にする。ステージがちょうど 1600 × 900 の画素で描かれる。枠、字幕、立ち絵は含めない。PNG を復号した画素の SHA-256 を比べるので、PNG の圧縮のしかたが変わってもハッシュは変わらない。
- `npm run stops -- [deck] [clipId …]` は比べるだけで、`--update` を付けると、挙げたクリップの基準を撮り直す。クリップを挙げずに更新すると、デッキから外したクリップの基準も消す。不一致を見て勝手に更新はしない。
- 違いを見つけたときは、クリップ、止まり、ハッシュの頭 12 字を短く報告し、実際の絵を `test-results/stop-differences/`（e2e）か `test-results/stops/`（コマンド）に、合わせて 20 枚まで残す。
- 最初の基準は、2026-10-17 に Chromium 151.0.7922.34（Playwright の chromium-1234）で撮った。どの絵も二度撮って一致を確かめ、別のブラウザのプロセスで走らせた e2e でも一致した。Chromium の版、OS、書体の描き方が変わったら、絵を見てから基準を撮り直す。
- **基準は、codex のサンドボックスの外で撮る。** 最初の基準は codex がサンドボックスの中で撮った。サンドボックスの外で e2e を走らせると、デモのデッキの 2 本（`quiz` と `sweep`、11 の止まり）だけが合わなかった。この 2 本は、デッキに同梱した書体ではなく、システムの書体（generic の `monospace` と、DOM の選択肢の文字）で描く。サンドボックスの中では、システムの書体の選ばれ方が違うと見られる（同梱の書体だけで描く LLM、三角関数、内角の和のデッキは、内でも外でも一致した）。2026-10-17 に、この 11 の止まりを外で撮り直した。

### 重なりの診断

`npm run check -- <deck> <id> --overlap --stops` は、すべての止まりで、`--overlap --at 1 78.742` は挙げた時刻で、次の四つを探す。見つけても終了コードは 0 で、`--strict` を付けると 1 になる。

1. 見えている二つの文字が、2 px 以上食い込んで重なる。
2. 見えている文字が、塗った矩形や線を引いた矩形の縁をまたぐか、縁から 2 px 以内に近づく。
3. 塗った矩形どうしが、どちらも相手を含まずに一部だけ重なる。
4. 文字か矩形が、ステージの外へはみ出す。

- しくみ: 撮影のページで、canvas の描画の命令を包み（`tools/inspect/canvas.mjs`）、1 フレーム分の文字と矩形の箱を集める。文字は実際に描いた範囲、矩形は塗りか線かと不透明度を持つ。検出は、箱の並びを受け取る純粋な関数（`tools/inspect/overlap.mjs` の `detectOverlap`）で、保持型のステージ（[stage.md](stage.md)）のノードの箱も、同じ形で渡せる。
- 誤検出を減らすため、次は数えない: 同じ文字を同じ所に重ねた描き方（色を重ねる描き方）、不透明度 0.5 未満のもの、後から不透明な矩形で隠れたもの、相手をすっかり含む背景やパネル、文字が中に収まる札や囲み、大きなパネルの縁にちょうど載る小さな端子や札（64 × 32 まで、パネルの面積の 5% まで）。
- 2026-10-17 に試した結果: LLM の `base` で 16 件、`mcpflow` で 57 件、`session` で 58 件（すべての止まりの合計）、三角関数の `define` と `ladder` は 0 件。`base` の 55.429 秒では、質問と答えが二重に描かれているのを、絵でも確かめた。`session` の最後には、「認証の設定は省略」とパネルの縁、「保存しない設定…」とコマンドの札の縁が 2 px 以内に近づいている所が 2 つある。直すかどうかは、作る側が絵を見て決める。
- 限界: 角の丸い要素や回した要素は、軸に沿った箱で近似する。Path2D、画像、DOM の文字、影は調べない。近いという注意だけで、見た目の良し悪しは決めない。
- 資源の上限: ブラウザの一つの操作に 15 秒、`check` と `stops` の全体に 540 秒（外の監督のプロセスが、子のプロセスごと止める）、`tok` と `pngdiff` に 30 秒。1 フレームの箱は 2,000 個、報告は 200 件まで。上限に達した検査は、成功とせず終了コード 2 にするので、対象を絞ってやり直す。
