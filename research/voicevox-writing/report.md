# VOICEVOX 原稿の書き方と API 調整の調査

調査・出典確認日：**2026-10-11 UTC**。対象：VOICEVOX Engine **0.25.2**、Core **0.16.1**、CPU・HTTP API、四国めたん（ノーマル）。将来のずんだもんと、話速 1.1／1.3／1.5も考慮した。利用者の経験・公開実装を主に集め、操作の成立は固定版の公式コードで照合した。出典の公開日・対象版は末尾に示す。

**Engine の起動、API 実行、合成、試聴は行っていない。** 本報告の「確実」は、指定を API に伝える方法の確実さを指す。自然さの最終判断と、この機械での再現確認は残る。プロジェクトの変更は行っていない。

## 要点

「ChatGPT」は、頻出語なら `チャットジーピーティー`・辞書 `accent_type=0` を候補にする。文の「ChatGPTへと」を直接制御するなら、助詞まで含む11モーラの句を `accent=11` にし、高さを再計算する。**`accent=3` は「トで上がる」という指定ではない**。「ツールを」は4モーラの句を `accent=4` にし、再計算後、2拍目「ウ」の `vowel_length` を必要なだけ延ばす。「エージェント」はボスの聴取で問題がないので現状を維持する。詳細は第3節。[S7]・[S18]

利用者の実践が複数一致するのは、**読みを確定→アクセント句と核を直す→個々の高さ・長さを調整、頻出語は辞書化**という順序である。ChatGPT のアクセント違和感は0.25.2の別利用者にもあるが、「GPT／MCP等を一律にこの核で読む」という合意や、ツールに共通する最適な長さまでは見つからなかった。[U1]・[U4]・[U5]・[U14]

道具には、既存の `[表記|よみ]` に加え、**デッキ語彙、意味としての平板指定、例外的な句指定、最終 AudioQuery への局所パッチ**が必要になる。Engine 辞書は全話者・全デッキで共有され、import は入替ではなくマージなので、デッキ辞書とは別の仕組みとして扱う。[S12]

## 2. Engine 0.25.2 の API 手段と再現手順

### 何ができて、何ができないか

以下は0.25.2タグのコードと固定依存版による確認。HTTP JSONは `accent_phrases`、`vowel_length` 等のsnake_caseを使う。利用者エディタのTypeScriptにある `accentPhrases`、`vowelLength` 等をそのまま送らない。[S2]・[S4]・[U21-code]

|手段|できること・使い方|できないこと／注意|根拠|
|---|---|---|---|
|本文の書換え／既存ruby|読みをカナや単位名へ差し替え、字幕を保つ|核、局所pitch、母音長は保証しない。語の置換で句の解析も変わり得る|[U7]・[U12]・[U15]、ローカルspec §6.6|
|`POST /audio_query`|通常文から初期AudioQueryを作る。`text`、`speaker`、`core_version`、`enable_katakana_english`|**この版のこのendpointには `is_kana` がない**|[S2]|
|`POST /accent_phrases`|通常文／`is_kana=true`のカナから、長さ・高さ計算済みの句配列を得る。queryの句配列を置換できる|戻り値はAudioQuery全体ではない。全体設定を別に保持する|[S2]|
|AquesTalk**風**記法|カタカナ、核 `'`、無音なし境界 `/`、無音あり境界 `、`、無声化 `_`、句末疑問 `？`|各句に核記号を一つ。長さ・任意pause秒・pitch数値は指定不可。**直接カナの文字表に「ー」はない**ので母音へ展開。独自クライアント記法と区別|[S5]・[S6]|
|`accent_phrases[].accent`|1始まりのアクセント位置を変更。1が頭高。句内下降を避ける候補は句末位置|`accent=0`を辞書平板0のつもりで直接入れない。**変更だけでは既存pitchは変わらない**|[S7]・[S18]|
|`POST /mora_data`|句配列からモーラ長→高さを再計算。読み・核・句境界の変更後に使う|JSON bodyは**句配列**。手調整した長さ・pitchを上書きする|[S2]・[S7]|
|`POST /mora_pitch`／`mora_length`|高さだけ／長さだけを再計算する|保持する手調整と、更新する値を選ぶ。話者styleとCoreは合成時と同じにする|[S2]・[S7]|
|`moras[].pitch`|各モーラの高さを局所変更する。予測値を基に調整|Hz／MIDI／半音の数として直接扱わない。無声pitch0へ一律に声を付けない。自然な数値は別問題|[S4]・[S7]・[S22]・[S23]|
|`vowel_length`／`consonant_length`|母音／子音の長さを秒のフィールドとして変更。速度適用前の値|個別モーラ音量はない。`consonant=null`の母音単独モーラに子音を捏造しない|[S4]・[S7]|
|`pause_mora`|既存の句末pauseを短縮・延長、nullで削除。必要ならpause付き句を作る|句境界とは別。`pause_mora=null`の句に `pauseLength`だけで無音は追加されない|[S4]・[S7]|
|`pauseLength`／`pauseLengthScale`|既存pauの長さを一律置換／倍率調整。0.25.2で利用可能|局所長を使うなら `pauseLength=null`。最終秒は速度でも割られる|[S3]・[S7]|
|`speedScale`|全音素長・pause・前後無音を速度で除算|語の一部だけの速度指定ではない。このプロジェクトでは文単位の三段|[S7]、spec §6.6|
|`pitchScale`／`intonationScale`|全体pitchへ `2**pitchScale` を掛ける／有声pitchの平均からの偏差を倍率調整|語の核を直す操作ではない。`intonationScale=0`は全体の一様化で、語彙の平板の代用にならない|[S7]|
|`volumeScale`|全体音量|ツールのウだけを強くするフィールドではない|[S3]・[S4]|
|`prePhonemeLength`／`postPhonemeLength`|発話前後の無音。速度適用前の秒|句中の待ちや語の長音の代用ではない|[S3]・[S7]|
|`is_interrogative`＋synthesisのupspeak|条件付きで最終母音を0.15秒追加し、pitchを+0.3（上限6.5）へ。自動追加を無効にもできる|語尾の既存母音を上げるだけの処理ではない。最後のpitch>0等の条件がある|[S7]|
|`query.kana`|生成された読みの観察・記録|**synthesisはこの文字列を無視する**。文字列だけを直しても音は変わらない|[S3]|
|`enable_katakana_english`|通常文の未知英字語をカナ化。既定true。英字間pau除去にも影響|全略語・モデル名の希望読みや核を保証しない。`is_kana=true`では無視|[S2]・[S10]|
|ユーザー辞書|表層形、カタカナ発音、品詞、核、優先度を持つ反復語を登録|単語の局所長／pitch／pauseは登録できない。文脈の句結合・核まで保証しない|[S8]・[S9]・[S15]・[S19]|
|辞書import|UUID→詳細単語モデルを既存辞書へマージ|デッキ切替・全置換ではない。簡略な「表記→読み」や配布前処理辞書を直接送れない|[S8]・[S12]|

局所pauseを最終音声でt秒にしたい場合、`pauseLength=null`を前提に、丸め前の対応は `pause_mora.vowel_length = t × speedScale / pauseLengthScale`。利用者記事の0.10〜0.15等が編集フィールドの秒か最終音声の秒か不明な場合は、そのまま移植しない。音素ごとのフレーム丸めで実時間には微小な差が出る。[S7]・[U14]・[U20]

Talkのpitch単位は、固定Core側の型だけではHz等の明記が得られなかった。開発者の公開推論実装には、正のF0入力を `exp` で戻してvocoderへ渡す処理があり、自然対数F0表現の裏付けになる。ただし配布Core0.16.1の個々のモデル内部まで一致を検証していない。ここでは予測されたpitchへの局所調整に留め、`pitchScale=0.1`を何半音という換算は提示しない。[S22]・[S23]・[S7]

### 読み・核・句を変えた後の手順

次は**未実行の実装手順**である。`speaker`は名称に反してstyle IDなので、すべて同一の四国めたんノーマルのIDを渡す。ずんだもんへ切り替えるときも同じ読みから、そのstyleで予測し直す。[S2]

1. 全文を `/audio_query` へ渡し、読み・句・モーラ・現在値を取得する。
2. 対象句の期待読みを照合し、核を変更する。句の分割・結合・読み変更があればここで行う。
3. `POST /mora_data?speaker=<style ID>&core_version=0.16.1` に **`query.accent_phrases` 配列そのもの**をJSON bodyとして送り、返る配列で置換する。既に決めた長さを保持して核に応じたpitchだけ直す場合は `/mora_pitch`。
4. 返った句に、局所母音長・子音長・pitch・pauseの手調整を適用する。以後、再計算するならこれらのパッチを再適用する。
5. 速度等の全体設定を反映し、**最終query**から印・期待音声長を計算する。同じqueryを `/synthesis` へ渡す。

合成は核を読んでpitchを自動再予測しない。`accent`変更→そのままsynthesis、または `query.kana`変更→synthesisという手順では目的に届かない。[S3]・[S7]

AquesTalk風を使う場合は、手順1で全体設定を用意し、次のリクエストで得た配列を置く。既に予測済みなので、さらに句の構造を変えなければ不要な再計算を重ねない。[S2]

```text
POST /accent_phrases
  ?text=<URLエンコードしたカナ>
  &speaker=<同じstyle ID>
  &is_kana=true
  &core_version=0.16.1

query.accent_phrases = 戻り値の配列
```

普通の本文や辞書で `チャットジーピーティー`、`ツール` と書くのはよい。直接カナ入力へコンパイルする段階で `ジイピイティイ`、`ツウル` にする。かな文字数とモーラ数は違い、`チャ`、`ティ`は各1、`ッ`は1である。[S5]・[S6]・[S9]

### 辞書を API で扱うときの具体事項

`GET /user_dict` はUUIDをキーにした詳細オブジェクトを返す。登録は `POST /user_dict_word`、更新・削除は `PUT`／`DELETE /user_dict_word/{UUID}`。登録・更新の単語情報はJSON bodyではなく **query parameter** に指定する。[S8]

```text
POST /user_dict_word
  ?surface=ChatGPT
  &pronunciation=<チャットジーピーティーをURLエンコード>
  &accent_type=0
  &word_type=PROPER_NOUN
  &priority=5
```

これは未実行の登録候補。ツールなら `surface=ツール`、`pronunciation=ツール`、`word_type=COMMON_NOUN`、`accent_type=0` が候補になる。品詞と優先度は全文での結果を見て選ぶ。省略時はPROPER_NOUN／5で、PUTは単語を作り直すため、変更しない品詞や優先度も明示する。[S15]

`accent_type`は0〜モーラ数、**0が語の平板**。`priority`は0〜10を受け、引数説明の推奨は1〜9。高いほど採用されやすいが、品詞と文脈のコストに関係し、望む句境界を直接指定する値ではない。品詞はPROPER_NOUN／COMMON_NOUN／VERB／ADJECTIVE／SUFFIX。[S8]・[S9]・[S15]

`POST /import_user_dict?override=true` のbodyはGET形式に対応する **UUID→UserDictWord詳細モデル**。`override`は指定が必要で、trueは同じUUIDを取り込み側で上書き、falseは既存側を保持する。別UUIDの同表層形は残り得る。ディスク保存ファイルにはcostなどAPIと異なる形式があるため、保存ファイルを無確認でそのまま送らない。[S8]・[S12]

## 3. ボスが気づいた三つの例への答え

### 1. ChatGPT：低く始め、トで上がり、その後を高く保つ

利用者は通常、まず核を動かし、足りなければ各音の高さを直し、繰り返す語は読み＋アクセントを辞書化している。0.25.2を試した[U5]もChatGPTのアクセント違和感を挙げる。ただし「ChatGPTは何番の核」という利用者間の一致は今回得られなかった。以下は**ボスの好む平板を固定版APIへ表現する処方**である。[U4]・[U5]・[U14]

|指定先|語だけ／助詞込み|値・記法|
|---|---|---|
|単語辞書|ChatGPTのみ|`pronunciation=チャットジーピーティー`, `accent_type=0`|
|AudioQueryの独立した句|ChatGPTのみ：9モーラ|`accent=9`|
|AudioQueryの独立した句|ChatGPTへと：11モーラ|`accent=11`|
|AquesTalk風|ChatGPTへと|`チャットジイピイティイエト'`|

モーラは `チャ1・ッ2・ト3・ジ4・イ5・ピ6・イ7・ティ8・イ9`。提示された末尾「エト」は後続の「へと」と考えられ、10・11になる。ChatGPTという**単語**の辞書へエトを含めない。実際の全文で句の範囲を確かめる。[S6]

辞書平板0と句の末尾位置が対応する理由は、OpenJTalkが**最終句の核0を句全体のモーラ数へ正規化**し、Engineがその位置を読むためである。単語末尾9に置いたまま助詞を同句に続けると、助詞で下降する尾高側の指定になる。平板の低い出だしは保持し、句内下降を作らないには助詞まで含めて末尾へ置く。[S18]・[S11]・[S7]

「トで上がる」ことを `accent=3` で書いてはいけない。核位置は上昇点ではなく下降に関わる位置である。非頭高の開始フラグは第2モーラへ置かれ、第2拍のッは有声母音ではないので、次の有声のトで上昇が聞こえる形を狙える。ただし核指定はモーラごとの絶対pitch一定を保証しない。[S7]

最も直接的には、対象句を末尾核に変更→`mora_data`（長さを維持するなら`mora_pitch`）→必要な場合だけ有声のチャを低く、ト以降の有声モーラを希望の高さへ修正する。**ッに有声pitchを足さない。** 辞書0は繰り返しに便利だが、付属語や複合語の結合で最終核が変わり得るため、全文の句・核・pitchを検査する。[S7]・[S19]

### 2. ツール：下降を避け、長音を聞き取れるようにする

まず核と長さを別々に直す。辞書候補は `ツール`・`accent_type=0`。直接句なら語だけは3、**「ツールを」まで同句なら4**。AquesTalk風は `ツウルオ'`。`ツ'ウルオ`の頭高から句末位置へ変更し、高さを再計算する。[S6]・[S7]・[S18]

次に、長音に当たる **2拍目ウの `vowel_length`** を局所編集する。対象句がツールをから始まるなら0始まり `moras[1]` だが、番号だけで当てず、`text=ウ`、母音u、子音なしという期待値を照合する。再計算後に行い、母音長パッチを上書きされないようにする。[S4]・[S7]

利用者の長さタブによる母音・子音の別調整[U4]、弱いu/iの最低長補正[U21-code]がこの操作に対応する。0.18という公開実装値は比較候補の出典になるが、ツールの確定値にはできない。まず基本1.3で「核だけ」と「核＋長音長」を比べ、決まった後に1.1と1.5を確認するのが次の検証案である。

既に読みがツウルなら、`ー→ウ`の書換えだけでは同じモーラが残る。さらにウを追加するより、既存のウの長さを直接制御するほうが目的を明示できる。ツの子音長、全体音量、全体抑揚を最初の代用にしない。[S4]・[S6]・[S7]

「弱い」が音量・音色を指す場合、長さだけで完全に解消する保証はない。個別モーラのvolumeフィールドはない。また実際にそのウが大文字U・pitch0なら無声化を別に検査する余地はあるが、今回の読み文字列からその原因とは判定できない。無声化の一括解除は採用しない。[S4]・[U21-code]

### 3. エージェント等：問題のない語は保つ

ボスの観察を採用し、読み・核・母音長を変更しない。カタカナ全部の平板化や `intonationScale=0` は、今回の二語の問題を超えて発話全体を変える。四国めたんの初期状態が自然だった末尾母音を伸ばして不自然にした利用者例もあり、変更を必要な語に限定する。[S7]・[U25]

**制御の確実さ**は、最終句の直接編集→再計算→局所pitch／長さパッチが最も高い。AquesTalk風は読み・核・句を直接指定できるが数値の長さは後段編集が必要。辞書は反復を省けるが最終句の検査が必要。自然さの順位は未試聴のため未確定である。[S2]・[S5]・[S7]・[S19]

## 4. この道具に入れるとよい仕組み

これは**仕様・実装前の提案**。読み取り対象は [AGENTS.md](../../AGENTS.md)、[docs/spec.md §6.6・§7.1](../../docs/spec.md)、[script.js](../../src/explorer/script.js)、[narrate.mjs](../../tools/narrate.mjs)、[core.mjs](../../tools/narrate/core.mjs)。現在の原稿は字幕／読み／印を分け、時間は全文queryの音素長で求める。演出の待ちは文分割とlead／tail／rest、話速は文単位の三段を保つ。

### 普通の原稿と上級指定を三層に分ける

|層|作者が書くもの|用途・処理|
|---|---|---|
|読み・反復語彙|既存 `[表記\|よみ]`、デッキの小さい語彙表|数字・略語・異読語。局所指定をデッキ語彙より優先する|
|アクセント句|意味としてのflat、必要時のみ句境界・全句カナ|核の例外。字の位置とモーラを照合し、対象句を限定する|
|調声メタデータ|文IDに結びつくモーラ長、pitch、pause等のパッチ|既存の声の外の待ちと区別する。最終queryへ適用し、印の計算にも反映する|

原稿の候補は `[ChatGPT|チャットジーピーティー;accent=flat]`。**現時点では未実装**である。flatを語彙の意味として保持し、Engine辞書へ出すときは0、句へ出すときは助詞込みの句末位置へ翻訳する。整数0を全経路で暗黙に共用しない。[S18]

ただし、ある語のflatを、別の名詞や述語まで結合された広い句へ盲目的に拡張しない。ChatGPTへと／ツールをのような想定句を照合し、範囲が違うときは要確認にする。必要ならその文だけ句境界を指定する。小書き字や促音を含む文字位置をモーラ数へ安全に対応させる。

公開クライアントには `コン[ニ]チワ,セ[カ]イ` という核記法、句の分割・結合実装がある。[U11-code]は参考になるが、既存の角括弧rubyと衝突する。またそのコードには「核省略で辞書平板0を往復できる」とは限らない経路があるので、平板記法をそのまま移植しない。句編集で末尾のpause・疑問属性をどの句に持たせるかも明示する。

### デッキ語彙は小さく、文脈と確認結果を持つ

推奨項目は、表層形・読み・意味としてのアクセント、品詞・優先度、別名と大小文字の方針、想定例文と助詞、出典、確認したEngine／Core／話者／話速。ChatGPT、ツールはflatの候補を持つ。MCP等は読み候補を持っても、核の標準値が調査で確定した扱いにしない。

長い表層形を先に、語の境界を考慮し、局所rubyを優先する。これにより白石／白石町、2倍／2倍速、mという変数／mという単位の衝突を減らす。[U13]・[U17]・[U18] 配布されている大量の置換辞書は候補集として扱い、Engineへ一括importできるアクセント辞書とみなさない。

Engine辞書を使うなら、narrateが管理する専用Engineの**辞書保存先を隔離する**案がよい。別案はEngine辞書を変更せず、デッキ語彙を前処理＋最終queryパッチに閉じる方式。どちらを採るかは実装時に決める。importの `override=true` は辞書入替ではないため、旧デッキ語彙の残存や別UUID重複を検査する仕組みが必要になる。[S12]

### 最終 query と印を同じデータから作る

```text
字幕・読み・印を解析
  → 局所読みとデッキ語彙を適用
  → 全文queryを取得／例外の句指定で置換
  → 核・句・音素変更に応じて再計算
  → 局所の長さ・pitch・pauseを適用
  → 最終queryから印と音声長を計算
  → 同じqueryで合成
```

現在は各印までのprefixも `/audio_query` に渡し、全文モーラの先頭と一致することを検査する。デッキ語彙をprefixにも同じ条件で適用する。句を手入力する経路では印→モーラの明示対応が必要になる。モーラ番号パッチには期待text／音素を併記し、読みや句が変わったら他語へ誤適用せず停止する。

局所の音素長・pause変更は印の時刻を動かすため、変更前queryの時刻を使わない。既存の93.75fpsでの音素ごとの丸め、疑問追加母音、実WAV長との差の検査も最終queryに対して維持する。

generationHashへは、正規化したデッキ語彙、記法版、句指定、局所パッチ、英語変換と疑問追加のflagを含める。既存の話者／style、Engine／Core、全体設定、速度も維持する。保存する読み `query.kana` だけでは後段のpitch／長さを記録できないので、最終queryまたはその内容とハッシュを残す。手調整を一律自動処理から保護する。[S3]・[U21]

### 未確認・今回の結論に使わなかったもの

- **実音と最適値**：この機械のChatGPTへと／ツールをの最終句・核・pitch・母音長。めたんノーマルとずんだもん各styleでの自然さ。API手段を確認したのであって、聴取で解決済みとはしていない。
- **略語の核の共通規則**：GPT／MCP／LLM／API／AI／o1について、独立した複数利用者が核まで一致する処方は得られなかった。読み候補は内容上の選択として提案した。
- **長音の比較**：通常テキストの `ー→母音` だけで弱長音が改善するという独立比較、1.1／1.3／1.5の知覚差、ツールの最適長。0.18等は作者の実装値である。
- **数字・記号の網羅的処方**：範囲、日付の慣用読み、複合単位、モデル名の数、句読点／空白別の固定pause秒。前処理と文脈で変わるため、意味の読み替えとquery検査を提案した。
- **話者の固有癖**：ずんだもんの「なのだぞ」は版・style・API値がなく、「prosody指定」という記事語も0.25.2の独立フィールドではない。めたん全般の弱母音という一般則も得られなかった。
- **公開実装の全体品質**：[U21-code]の補正処理を読んだが全store呼出順・保護フラグの実行は未検証。[U11-code]も全クライアントの再計算経路は未照合。コードの存在と自然さを分ける。
- **未取得の詳説**：[U14]の「している」の画像内核値、動画の本文・音声。[U10]のYouTube説明には音の長さの項目があるが具体処方を得ていない。ニコニコ原動画[U3]は転載説明の範囲を明記した。
- **媒体の偏り**：note・ブログ・Qiita・Wiki・公開ツールを主な証拠にできた。有限補足検索ではX／ニコニコ大百科から語固有の再現可能な本文は追加取得できず、Zennの長音検証例[除外1]はVOICEPEAKだったため除いた。媒体名を埋めるための一般記事を証拠人数に加えなかった。
- **pitchの内部単位**：公開推論コードの対数F0の裏付けはあるが、Core0.16.1配布モデル内部までの一致は未照合。歌唱APIのF0をTalkへ転用しない。

## 6. 問いと計画の変化、次の行動

初期の「書き方の規則を集める」という問いは維持したが、規則を道具に入れるには、**辞書の平板0と句の末尾核の違い、再計算、Engine辞書の共有範囲**が不可欠だと分かった。そのため公式照合を初回と補足の二つに分け、最後に利用者実装の有限照合を加えた。計画と各単位の資料は [log.md](log.md) に残した。

|派生質問|判断・結果|
|---|---|
|極端な長音のかすれ対策を普通のツールに使うべきか|本題に必要なので追究。何秒もの叫びと既存一拍の弱長音を分け、子音挿入をツールの初期処方にしない|
|複数サイトにある同じTipsを何人の証拠と数えるか|確かさDに必要なので追究。参照・転載・同じ作者を分け、単なる多数掲載を独立実験としない|
|不要pauseを全部削除すれば自然になるか|原稿の設計に必要なので追究。意図した「ため」が消えた利用者例を得て、局所指定と手調整保護を提案|
|全自動ナチュラル化、全版・全話者、大辞書の品質評価|本題の範囲を超えるため保留。自動補正の導入時に別の比較が必要|

次は、仕様案としてデッキ語彙・flat・調声メタデータ・印／ハッシュの契約を決める。その後、**起動・合成の承認を得た段階で**、1-1の実文を基本1.3で「現状→核のみ→長さのみ／核＋長さ」の少数比較にする。問題のないエージェントも比較に残す。採用候補だけ1.1と1.5を確認し、最終queryと聴取メモを語彙の根拠にする。ずんだもんは同じ読み・核を初期候補にしても、pitchと長さを別styleで再計算・確認する。今回はこの比較も、仕様・コード変更も実施していない。
