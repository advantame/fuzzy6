### 引き継ぐ事実と根拠

1. **モデルへの入力とAPIのJSONは同じ層ではない。** agent-facts B1/B2はAnthropicのname/description/input_schema、Chat Completionsのfunction/parameters、Responsesのfunction itemを区別する。Anthropicは定義・設定・systemから専用system promptを作る。出典（既存取得）：https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools 、https://developers.openai.com/api/docs/guides/function-calling 。今回、定義の説明が選択に効く根拠とHF template側の担当を追加確認する。
2. **外側の実行主体。** B1のclient toolsはアプリ側、server toolsはAnthropic側。教材の「アプリ」はassistant-facts A2の、画面・サーバー等モデルの外で会話を受け渡すプログラムという広い用法を引き継ぐ。全API利用者が全toolを自分で実行するという意味にはしない。https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview 。
3. **呼出し／結果のAPI形式。** Anthropic assistant contentのtool_useにid/name/input、結果は直後user内のtool_resultでtool_use_id対応。OpenAIはtool_calls→role:toolとfunction_call→function_call_outputを区別する。APIのuserは人の手入力を意味しない。B1/B2根拠：https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls および上のFunction calling。

5-1 ツールを使う（`tools`）:

1. チャットボットを作っていて、「あしたの京都の天気は？」と聞かれたとしましょう。
2. LLM が学んだのは、学習に使った文章だけで、あしたの天気は、まだどこにも書かれていなかったわ。
3. このまま続きを書かせると、それらしい天気を、もっともらしく書いてしまうかもしれないの。
4. 一方で、天気の予報を返してくれるプログラムなら、もうあるわね。
5. でも、LLM にできるのは、文章の続きを書くことだけで、プログラムを動かすことはできないの。
6. そこで、プログラムを動かす役は、アプリに任せるの。
7. LLM には、答えの代わりに、「京都の天気予報を調べたい」という頼みを書かせるのよ。
8. アプリは、その頼みを読んでプログラムを動かし、返ってきた予報を、文書に書き足すわ。
9. それをもう一度 LLM に読ませれば、予報を手がかりにして、答えを書けるわね。
10. ずんだもん: LLM が、自分で調べに行ったわけじゃないのだ？
11. ええ。LLM は頼みを書いただけで、プログラムを動かしたのは、アプリよ。
12. こうして、アプリが LLM の頼みで動かすプログラムを、ツールと呼ぶわ。
13. LLM がツールを使う頼みを書くことは、ツール呼び出しと呼ばれているの。
14. ツールの場所には、入力を受け取って、結果を返すものなら、何でも置けるの。
15. 天気のほかにも、検索、計算機、コマンドを打つシェルなど、いろいろなものがあるわ。
16. この章では、この一回のやりとりを、順に細かく見ていきましょう。

5-2 ツールの定義（`toolspec`）:

1. LLM にツール呼び出しを書かせるには、まだ足りないものがあるの。
2. LLM が知っているのは、渡された文書に書かれたことだけよ。
3. どんなツールがあって、どう頼めばいいのかが書かれていなければ、頼みようがないわ。
4. そこで、アプリには、使えるツールの説明を、文書の頭に書かせておくの。
5. 説明には、ツールの名前と、何をするのか、どんな入力を受け取るのかを書くわ。
6. こうして一つのツールを説明したものを、ツールの定義と呼ぶの。
7. アプリを作る人は、定義を、決まった形のデータで書いておくの。
8. LLM に渡すときには、それが、コンテクストの中に、文字として書き込まれるのよ。
9. 天気のほかに、検索や計算のツールも並べておけば、LLM は、質問に合うものを選んで頼めるわね。
10. ずんだもん: ツールの中のプログラムは、LLM には見えないのだ？
11. 見えないわ。LLM にわかるのは、定義に書かれた言葉だけなの。
12. だから、何をするツールで、どんなときに使うのかを、定義にわかりやすく書いておくことが大切なのよ。
13. 定義もコンテクストの一部だから、ツールを増やすほど、読ませる文書も長くなるわ。

5-3 呼び出しを書く（`toolcall`）:

1. 定義が書いてあれば、LLM は、答えの代わりに、ツール呼び出しを書けるわね。
2. でも、LLM が書くのは、どれも同じテキストよ。
3. このままだと、アプリには、それが答えなのか、ツールへの頼みなのか、見分けがつかないの。
4. 頼みだとわかっても、どのツールに何を渡せばいいのかを、自由な文章から読み取るのは大変ね。
5. そこで、ツール呼び出しを書く形を、決めておくの。
6. 始まりと終わりに、呼び出しの印を書き、その間に、ツールの名前と入力を書くわ。
7. 名前と入力は、プログラムが読み取りやすい、JSON という形で書くの。
8. そして、この形で書くように、LLM を学習させておくのよ。
9. 呼び出しを書き始めるかどうかも、次のトークンを選ぶのと同じよ。
10. アシスタントの印のあとで、呼び出しの印が選ばれれば、呼び出しが始まるわ。
11. 続けて、ツールの名前と入力を、トークンごとに書いていくの。
12. 終わりの印が出たら、アプリはそこで書かせるのを止めて、名前と入力を読み取るわ。答えの終わりの印を見張らせたのと、同じやり方ね。
13. Anthropic の API では、呼び出しで止まったことを、tool_use という値で知らせてくれるわ。
14. ずんだもん: LLM が、勝手にツールを動かしてしまうことは、ないのだ？
15. LLM が書けるのは、呼び出しの文字だけよ。本当に動かすかどうかを決めて、動かすのは、アプリなの。
16. 印の書き方は、モデルごとに違うわ。画面の下は、gpt-oss というモデルの、実際の書き方よ。

5-4 結果を書き足す（`toolresult`）:

1. アプリは、呼び出しから読み取った名前と入力で、ツールを動かすわ。
2. でも、返ってきた結果は、アプリの手元にあるだけで、LLM からは見えないの。
3. そこで、アプリには、結果に「ツールの結果」という印を付けて、文書に書き足させるの。
4. その後ろに、アシスタントの印だけを、また書いておくわ。
5. そして、この文書を、もう一度、頭から LLM に読ませるの。

### 判定の前提

- 「言える」は、この章のテキスト生成モデル・外部ツール・正常動作の作例という既存の文脈で維持できるもの。「限定すれば言える」は、例・担当・形式・条件を明示して初めて誤解なく使えるもの。「言えない」は、原文の中心的な断定を置き換える必要があるもの。問いや章の案内には独立した技術命題がないため、対話として維持できれば「言える」とする。
- 「アプリ」は既存A2の広義（モデル外の入力整形・実行・会話管理のプログラムを含む）。利用者端末の画面部分だけを意味しない。API側の整形・生成停止と、利用アプリの実行判断は図注で区別する。
- 言い換えは事実上の問題を直す候補であり、最終的な語り・字幕整形は制作側の担当。文の統合・分割を許す。以下の番号は固定された第1稿に対応する。

### 決めたこと6項目の横断確認

1. **5本の並びと題名**：維持可能。ツール→定義→呼出し→結果→反復という構成に事実上の矛盾はない。「ツールの定義」はU5-S3の用例あり。
2. **京都のあしたの天気**：題材は維持。ただし「学習文章にまだ書かれていなかったから」という採用理由は5-1.2の修正に合わせて撤回し、最新予報を外部から入れる必要のある例と位置づける。「未来の実際の天気」と「いま公表されている予報」を分ける。図の24℃・晴れ・雨は説明用。
3. **三つのツール**：`get_weather(city)`、`search_web(query)`、`calculate(expression)`は教材が定義する契約の例として可能。実在API共通の関数名・引数ではない。追加の整合点：天気の入力がcityだけなので、この作例の定義を「その都市の、あしたの予報を返す」と明示するか、「日別予報を返し、その中からあしたを読む」とする必要がある。日付を入力で選べると描くなら引数追加が要る。検索も「関係する文章を返す」はこのツールの仕様であり、すべての検索APIの返却形式ではない。
4. **LLM・アプリ・画面・ツールの配置**：維持可能。物理的な所在地の図ではなく役割の模式図とする。呼出しと結果は入力文書の位置から動いてよいが、実際の実行を起こす主体はアプリの箱で示す。API提供元のserver toolや入力整形もモデル外であり、すべてが利用者端末にある意味にはしない。旧layoutとの互換性は実装課題なので本調査では検証していない。
5. **印の外枠色**：紫=外側が入力へ用意するもの、墨=生成するものという図の約束は使える。固定された共通token一覧や全APIでの生成境界を主張しない。rendererがassistant headerの一部までprefixとして用意する形式もある。朱=要求、緑=結果は教材の凡例であり、仕様の色ではない。
6. **5-1末尾の章内目次**：事実上の問題なし。目次は5-2の定義、5-3の要求、5-4の結果、5-5の反復に対応する。
