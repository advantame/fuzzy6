# 4章「チャットボット」第1稿：事実確認

## 要約と判定方法

**章の流れは使えるが、例として見せる範囲と、モデル・アプリ・学習の区別を明示する必要がある。** 会話形式、SFT、比較評価による調整、履歴を使う応答は、それぞれ一次資料で説明できる。一方、すべてのモデルが同じ三段階で学ぶ、会話を毎回一から計算する、メモリー製品の内部がすべて同じ、という説明にはできない。[チャット形式][A2-HF]、[SFT][A3-T]、[Llama 3の学習][A4-L3]、[会話状態][A5-S]、[キャッシュ][A5-P]

**優先して置き換えるのは4-6.4と4-6.10。** 「ありそうな続きだから、確かめた事実ではない」という推論は成立しない。また、検索した資料を入力に加える構成は、モデル自身が道具の呼出しを決めなくても作れる。「自然な文章でも正しいとは限らない」「検索などの道具をアプリにつなぐ方法がある」とすれば、5章へ正確につながる。[Kalaiほか §3・5][A6-K]、[RAG §2][A6-R]

対象は[decks/llm/README.md](../../decks/llm/README.md)の「2026-10-15（4 章を作り直す）」にある第1稿の全59項目。基準日は **2026-10-15**、今回の外部資料の取得日は **2026-10-14 UTC**。発表日・版の日付とは区別する。原稿の固定全文と取得箇所は[log.md](log.md)にある。対象段のSHA-256は `713a0bc5924c50b014b554eb55881d0acf5cb25635287860d77ac11106f112c5`。

## A1：事前学習の目的と、入力に置く例

InstructGPT論文のFigure 9には、故意におかしな前提の質問に対し、GPT-3が別の質問から続きを始める例がある。その後には回答や別のQ/Aも続くため、「質問だけを延々と並べる実測」とはしない。Figure 8には執筆指示のあとに別の執筆指示を続ける例もある。いずれも挙動を示すために選ばれた例で、頻度の測定や日本語の首都問題での再現性の証拠ではない。[A1-P2 Figure 8・9][A1-P2]

事前学習の目的と、指示に沿う回答を学ぶ目的は区別できる。ただし「答えようとしていない」とモデルの意図を断定する必要はない。何を予測するように学んだかを説明すれば足りる。[A1-O1][A1-O1]

GPT-3のfew-shotでは、入力に課題の入出力例を並べ、新しい入力への続きを生成させる。課題ごとの重み更新はしない。Q:/A:形式の質問応答もある。「質問：／答え：」はその説明用翻案として使えるが、形式を付ければ正しい答えになるという保証ではない。few-shotは入力中の手本、SFTはパラメータを更新する学習、チャットテンプレートは発言等を整形する形式である。[A1-P1 §2・3.2・Appendix G][A1-P1]、[A2-HF][A2-HF]

## A2：会話の列、終端、外側の処理

文字の会話をrole付きメッセージから一続きの列へ整え、トークンの番号列として渡す説明は使える。「一本の文書」は見せ方であり、プレーンテキストファイルがそのままモデルに入るという型の説明ではない。画像・音声を含む全入力を普通の文章へ還元する説明にも広げない。[A2-HF][A2-HF]、[A2-LT][A2-LT]

「アプリ」は本教材では、**画面やサーバーなど、モデルの外側で会話を受け渡すプログラム**と定義するとよい。APIを呼ぶ側が構造化メッセージを送り、提供側で最終整形する場合も含む。これは資料を踏まえた教材上の定義で、公式用語の唯一の定義ではない。[A2-HC 導入][A2-HC]、[A2-T][A2-T]

| 区別 | Llama 3の公式コード | Harmonyの取得本文 |
|---|---|---|
| 発言の開始 | 区切りトークンとrole等でheaderを作る | 開始印にrole等のheaderが続く |
| 生成の開始 | 空のassistant headerを末尾に追加する例 | headerの途中からchannel等を生成する場合もある |
| 発言の区切り | `<\|eot_id\|>` | `<\|end\|>` |
| 停止 | stop_tokensや長さを外側が判定 | 回答完了は`<\|return\|>`、道具へ渡す停止は`<\|call\|>` |
| 指示 | systemを扱う | 通常のアプリ側指示をdeveloperに置く区分がある |

出典：[Llama 3 tokenizer.py][A2-LT]、[generation.py][A2-LG]、[Harmony format.md][A2-HR]。Harmonyの綴りは取得時の本文に従った。公開gpt-oss向け資料を、全OpenAI製品の内部形式の証拠にはしない。形式を混ぜた実機図は作らない。日本語の「ユーザー」等は図の説明ラベルで、一語ずつが特殊トークンという意味ではない。

モデルが出した終了印を検出して生成を止めるのは外側のプログラム。発言が一区切りしただけで回答全体が終わるとは限らない。出力には制御情報等もあり、全部をそのまま吹き出しに出すわけではない。生成中から本文を表示することもできる。[A2-LG][A2-LG]、[A2-HC][A2-HC]、[A2-S][A2-S]

## A3：手本の学習、損失、データの数え方

SFTでは手本の次トークンを予測するようパラメータを調整する。「外れを数える」は0/1の誤答数と聞こえやすい。通常の損失は手本のトークンに割り当てた確率を使うため、「答えの部分の予測を手本と比べる」と説明する方が3章に合う。[A3-T][A3-T]

回答部分だけを損失の対象にする実例は、Llama 2・3、Alpaca、TRLにある。**頼みを損失から外しても、入力から消すわけではない。** Alpacaではpromptを入力に残し、その位置のlabelを無視する。共有パラメータの更新まで「質問に関わる部分は学習しない」と解釈しない。TRLには全体を対象にする設定もあり、業界全体の採用率は測っていない。InstructGPT論文ではmaskの明示を今回確認できず、回答のみという内部実装の断定には使わない。[A3-L2 §3.1][A3-L2]、[A4-L3 §4.1.3][A4-L3]、[A3-A preprocess][A3-A]、[A3-T][A3-T]、[A3-I §3.5・C.1][A3-I]

SFTは学習方法の広い名称。指示チューニングは指示で表した課題への応答を学ぶ調整を指す。本節の手本学習は両者に当たるが、SFTのすべてが指示・会話の学習ではない。また、公表例にはモデル生成・選別による手本もあり、人が一から書く会話だけに限定できない。[A3-F abstract][A3-F]、[A3-T][A3-T]、[A4-L3 §4.2][A4-L3]、[A4-Q §4][A4-Q]

| InstructGPTのSFT | labeler由来の入力 | customer由来の入力 | 合計 |
|---|---:|---:|---:|
| 訓練 | 11,295 | 1,430 | **12,725** |
| 検証 | 1,550 | 103 | **1,653** |

出典：[A3-I Appendix A.3 Table 6、A.4 Table 9][A3-I]。約1万3千は訓練prompt件数を丸めた値。人の人数、トークン数、比較ペア数、独立した頼みの種類数ではない。同じ指示からfew-shot例の組合せを変えて複数のデータ点を作る処理も記されている。

InstructGPTではSFTに続く比較評価を使った調整で選好評価が改善した。ただし、比較用SFTとRL初期化用SFTは学習条件が同一ではなく、「同じ完成checkpointにPPOだけを加えた単一要因の比較」としない。SFTだけではよい回答ができない、全モデルにRLHFが必須、とも言えない。[A3-I §4.1・C.1・C.3][A3-I]

## A4：InstructGPTの例と、現在へ広げられる範囲

**4-4.1〜4の「言える」はInstructGPTの手順としての判定。** 冒頭に「次は、2022年のInstructGPTで使われた方法を見てみましょう」などを置き、帯に「InstructGPTで使われた方法の例」と明記する。その前提なら、人の順位付け→報酬モデル→PPOによる調整の概観は妥当。実際には基準モデルからの逸脱を抑える項もあり、PPO-ptxでは事前学習勾配も混ぜるため、「点を最大にするだけ」とは説明しない。[既存T1](../llm-facts/report.md)、[原論文][A3-I]

1.3B（13億）対175B（1750億）の結果は、研究で評価したAPI由来の頼みへの回答を人が比較した選好の結果。SFT等を含む追加学習の成果であり、小さいモデルの全能力が大きいモデルを上回った、PPOだけの効果、大きさは無関係、という結論ではない。初代ChatGPTがGPT-3.5系列に対話例と人の比較を用いたRLHFを適用したことも、先行調査から引き継げる。[既存T1](../llm-facts/report.md)、[既存chatbot-facts](../chatbot-facts/report.md)、[InstructGPT公式説明][A1-O1]、[初代ChatGPT Methods][H-CHAT]

## A5：履歴、状態、キャッシュ、メモリー

手動で履歴を送るChat CompletionsやMessagesの説明は先行調査を引き継ぐ。Responsesには手動管理のほか、`previous_response_id`やConversationsによる状態継承がある。Conversationsの契約では保存済み項目が今回の入力の前に加えられる。IDは外側が履歴を参照するための指定であり、LLMが短いID自体から会話を思い出すという説明にはしない。[既存T2](../llm-facts/report.md)、[A5-S][A5-S]、[A5-M][A5-M]、[A5-R conversation][A5-R]

**文脈に含めること、通信で再送すること、同じ計算を繰り返すことは別。** 入力の共通部分について保存したKV状態を再利用できるため、「毎回はじめから読み直す」は全文再計算と誤解されやすい。キャッシュは入力に応じた中間状態で、学習パラメータの更新でも昔の回答の再掲でもない。題名は「会話を引き継ぐ」などを勧める。[A5-P][A5-P]

窓に収める処理には、省略、要約・圧縮、超過時のエラーがある。Responsesの取得仕様では`truncation=disabled`が既定で超過はエラー、`auto`では先頭の項目から落とす。圧縮は上限に届く前にも行える。すべての圧縮が人に読める要約文になるわけではない。窓から原文を外すことと、外部に保存した会話の削除も別である。[A5-R truncation][A5-R]、[A5-C][A5-C]

ChatGPTの公式説明は、過去会話や保存情報を応答に使う機能を説明するが、毎回どのroleへどの文章を加えるかまでは開示していない。一方、Cookbookには保存したプロフィールや長期メモを文字列化し、instructionsへ組み込む公開例がある。**後者はChatGPT内部の仕様書ではない。** 保存情報を入力へ加える「作り方の一例」として図示する。[A5-H][A5-H]、[A5-N Memory Injection・Step 6〜8][A5-N]

## A6：事実性、評価の誘因、検索への接続

ハルシネーションは、ここでは事実でないことをもっともらしく述べる現象として説明できる。頼まれて作った物語や意図的な嘘と同一視しない。次トークン生成という形式から、事実の確認が不可能だと結論することはできない。[A6-K §1・3][A6-K]

Mata v. Aviancaは既存T3から引き継ぐ。2023年6月22日の命令は、架空の判決文6件と、その後の確認回避や虚偽説明等を扱った。Peter LoDuca、Steven A. Schwartz、Levidow, Levidow & Oberman P.C.の**合計5,000ドルの連帯負担**であり、各人に5,000ドルずつではない。語りでは「AI」、画面では記録に沿って「ChatGPT」とする案は維持できる。AIを使ったことだけへの制裁とはしない。[既存T3](../llm-facts/report.md)、[制裁命令 pp.1–2・7・12–13・31・33–34][H-MATA]

Kalaiほかの2025年の分析は、正答だけに点を付け、誤答と棄権を同じ無得点にする評価が当て推量を後押しするという議論を含む。誤答そのものに加点する意味ではなく、全評価が同じ、原因はこれだけ、という主張にも広げない。理論の仮定を離れた全モデル共通の誤り率の定理として紹介しない。[A6-K §4][A6-K]

主な対策として、資料を検索して内容を入力に加えること、不確実な場合に断定を避けたり問いを確認したりすること、誤答と棄権を区別して不確実性の扱いも評価することを挙げられる。検索資料も誤り得るし、検索で答えが得られない場合もある。検索は完全な解決ではなく、モデル自身が検索開始を選ぶことも必須条件ではない。[A6-R §2・4.3・Broader Impact][A6-R]、[A6-K §5][A6-K]、[A7-L][A7-L]

## 3章との整合と、制作へ渡す注意

以下は資料を踏まえた制作提案。追加の実装要件や全製品の仕様ではない。

- **例の札を揃える。** 首都の出力は「例（説明用）」、問題集の類推は「イメージ」、日本語の印は「形式の一例」、三段階の帯は「InstructGPTで使われた方法の例」。回答のみの損失の図をInstructGPTの非公開実装の再現にしない。[A1-P2]、[A2-LT]、[A3-L2]、[A3-I]
- **入力の例と学習の手本を分ける。** 4-1は入力に例を置く。4-3はパラメータを更新する。回答位置だけで損失を求める場合にも、頼みは入力に残す。[A1-P1]、[A3-A]
- **本体と外側を分ける。** 整形、トークン化、選択、停止判定、表示をすべてモデル本体の計算へ戻さない。生成順、モデル計算回数、通信回数、表示回数を同じ回数にしない。[既存K1・K5](../concept-facts/report.md)、[A2-LG]、[A2-S]
- **記憶の意味を分ける。** 学習パラメータ、今回の文脈、外部に保存した履歴・メモ、再利用する計算状態は別。毎回全文を走査する動きや全履歴を再送する矢印を、全方式共通の図として描かない。[既存K6・K7](../concept-facts/report.md)、[A5-S]、[A5-P]、[A5-N]
- **評価の意味を揃える。** 望ましい手本、人の選好、報酬モデルの点、検証可能な正答、事実の正確性は同一ではない。4-4の選好改善が4-6の誤りの消滅を意味しない。[A3-I]、[A4-Q]、[A6-K]
- **長い案は文に分ける。** 短さのため必要な限定を消さず、[spec §6.6](../../docs/spec.md)の語り・字幕の単位へ分ける。読み、字幕の行数、絵と音の確認は制作段階で行う。

## 不確実性、問いの経緯、次の行動

確認できていないのは、日本語の首都例の実測結果・頻度、InstructGPTのSFTの損失mask、非公開モデルの詳細な学習工程と業界全体の採用率、ChatGPTメモリーの入力への具体的な組込み位置・表現である。system指示や日本語訳の使用頻度も測っていない。見つからなかった記述を、機能や実装が存在しない証拠にはしていない。

研究は「問い×資料群」の10単元で進めた。計画改訂1では、A3から派生した「何を損失として測り、何を一件と数えるか」を追究。改訂2では、A3/A4から派生した「評価の作り手・評価基準・調整法」の区別を加えた。A6では「検索とモデル主導の道具呼出しは同じか」を原文の判定に必要な範囲で追究した。いずれも元の問いのための整理で、別の目的に置き換えてはいない。最新全製品の工程・採用率、非公開内部の解明、5章全体の監査は保留した。最新の計画に対する全10単元と59項目の横断点検は完了している。[調査ログ](log.md)

推奨する次の行動は次の順。

1. 4-6.4と4-6.10を置き換え、31項目の限定を原稿へ反映する。4-5の題名と三段階の帯の範囲も合わせる。
2. 現状の首都例は作った例として制作する。実測として紹介したくなった場合だけ、モデル・入力・生成条件を固定して別途測る。
3. 5章への接続で、誰が検索開始を判断し、誰が検索を実行し、何が入力に加わるかを確認する。9章のキャッシュ説明とも整合させる。両章全体の監査は今回未実施。
4. 特定の最新製品名や内部図を追加する場合は、その版に対象を絞って公開根拠を追加確認する。非公開部分は推測で埋めない。
5. 採用原稿を語りの文へ分け、字幕・読み・合成時間・実際の動きを制作手順に沿って確認する。本報告ではそれらの検証はしていない。
