11. すると、つなぐプログラムは、3 たす 4 で、7 本になるわね。
12. この決まりを、MCP と呼ぶわ。Model Context Protocol の略よ。
13. サービスの側で答えるプログラムを、MCP サーバーと呼ぶの。
14. MCP は、2024 年 11 月に Anthropic が公開し、2025 年 12 月には、Linux Foundation のもとの団体に寄贈されたわ。
15. ずんだもん: 差しこみ口の形を、そろえたってことなのだ？
16. そうよ。形がそろっているから、一度作った MCP サーバーを、いろいろなハーネスにつなげるわ。

7-3 定義を取り寄せる（`mcpflow`）:

1. では、GitHub の MCP サーバーを、このハーネスにつないでみましょう。
2. ハーネスは、まず、サーバーに、使えるツールの一覧を尋ねるわ。
3. サーバーからは、ツールの名前と、何をするのか、どんな入力を受け取るのかが返ってくるわ。
4. 5 章で見た、ツールの定義と同じ中身ね。
5. ハーネスは、それを、シェルの定義と並べて、文書の頭に書き足すの。
6. LLM は、その定義を読んで、Issue を検索するツール呼び出しを書くわ。
7. ハーネスは、その呼び出しを、MCP の形に直して、サーバーに送るわ。
8. サーバーは、GitHub の API を呼んで、見つかった Issue を返してくれるわね。
9. ハーネスは、それを、ツールの結果として、文書に書き足すわ。
10. ずんだもん: LLM は、MCP のことを知らなくても、いいのだ？
11. ええ。LLM が読むのは定義と結果で、書くのはツール呼び出しだけよ。
12. MCP でやりとりするのは、ハーネスとサーバーなの。
13. 見つかった Issue の #128 には、時間切れの知らせはあっても、原因は、まだ書かれていないわね。
14. ただ、サーバーをいくつもつなぐと、定義が増えて、毎回読ませる文書が長くなるわ。
15. そこで、はじめは名前と短い説明だけを入れておいて、要るときに、定義の中身を取り寄せさせる工夫もあるの。

7-4 記録を残す（`session`）:

1. ここから、エージェントは、ログやコードを読み、コマンドを試しながら、原因を探していくわ。
2. ツール呼び出しと結果が、一本の文書に、次々と積もっていくの。
3. 依頼を受けてから報告するまでの、この一続きのやりとりを、セッションと呼ぶわ。
4. 積もった中身の多くは、ツールの結果よ。
5. ファイルの中身やコマンドの出力は、一つで何千トークンにもなるわ。
6. ずんだもん: 途中でパソコンを閉じたら、どうなるのだ？
7. このままだと、ハーネスが持っている文書は消えて、一から調べ直しになるわね。
8. そこで、ハーネスには、文書に書き足すたびに、同じものをファイルにも書き残させましょう。
9. 続きをするときは、そのファイルから文書を組み立て直させれば、途中から再開できるわ。
10. Claude Code や Codex CLI も、セッションを手元のファイルに残して、あとから再開できるようにしているわ。
11. 記録は、エージェントが何を読み、何を動かしたかを、人があとから確かめるのにも使えるの。
12. ただ、記録を残しても、LLM に読ませる文書が短くなるわけではないわね。

7-5 窓に収める（`compact`）:

1. 調べものが続くと、文書は、コンテクストウィンドウの上限に近づいていくわ。
2. 4-5 では、会話が長くなったとき、古い部分を省いたり、要約したりしたわね。
3. エージェントの文書で、まず目をつけたいのは、古いツールの結果よ。
4. 一度読んだファイルの中身は、要るときに、もう一度ツールを呼べば、読み直せるわ。
5. そこで、ハーネスに、古いツールの結果を消させて、消したという印だけを残させましょう。
6. それでも上限に近づいたら、ここまでのやりとりを LLM に要約させて、その要約から続けさせるの。
7. 文書をこうして要約で短くすることを、コンパクションと呼ぶこともあるわ。
8. ずんだもん: 要約したら、大事なことが抜けてしまわないのだ？
9. 抜けることもあるわ。だから、どのセッションでも守らせたい決まりは、文書の外のファイルに書いておくの。
10. たとえば、「テストは、このコマンドで動かす」「本番のデータベースには触らない」といった決まりよ。
11. ハーネスは、セッションの始めに、そのファイルを読んで、文書の頭に入れるわ。
12. こうしたファイルには、CLAUDE.md や AGENTS.md という名前が使われているわね。
13. ただ、長い文書を読ませられても、どこでも同じようにうまく使えるとは限らないわ。8 章で見ていきましょう。

7-6 子に任せる（`subagent`）:

1. 調べを進めると、原因の候補は、三つにしぼれたわ。
2. データベースの設定、10 月 6 日の変更、その日のアクセスの数よ。
3. 一つずつ調べると、それぞれの結果が、また文書に積もっていくわね。
4. そこで、ハーネスに、別のエージェントを呼ぶツールを持たせましょう。
5. LLM がそのツールの呼び出しに依頼を書くと、ハーネスは、新しい文書を作って、別のくり返しを回すわ。
6. 呼ばれたエージェントは、自分の文書の中で調べて、短い報告だけを返すの。
7. もとの文書に書き足されるのは、その報告だけよ。
8. 三つの調べものは、並べて同時に進められるわね。
9. このように、仕事の一部を任されて、自分の文書で動くエージェントを、サブエージェントと呼ぶわ。
10. ずんだもん: 任せれば、速くて安くなるのだ？
11. 速くはなっても、安くなるとは限らないわ。サブエージェントも、それぞれの文書を、何度も LLM に読ませるからよ。
12. Anthropic は 2025 年 6 月、調べものの社内の評価で、サブエージェントを使う仕組みが、一つのエージェントより 90.2% 高い成績だったと報告したわ。

14. 三つの報告を読んだ LLM は、10 月 6 日に、データベースへの接続の上限を下げた変更が原因だ、と突き止めたわ。

7-7 任せる範囲（`safety`）:

1. あとは、設定を直して、テストを通し、Issue に報告すれば、仕事は終わりね。
2. どれも、本当にファイルやサービスを変える操作で、間違えると、元に戻せないこともあるわ。
3. それに、LLM は、読んだ文書の中の指示に、つられてしまうこともあるの。
4. たとえば、Issue のコメントに「このデータベースを消して」と書かれていたら、それを、ユーザーからの指示と取り違えるかもしれないわ。
5. ツールの結果にまぎれこませた指示で、LLM を操ろうとすることを、プロンプトインジェクションと呼ぶわ。
6. 2025 年 5 月には、Issue に仕込んだ指示で、エージェントに、公開していないリポジトリの中身を書き出させられる、という報告も出たわ。
7. ずんだもん: LLM に「気をつけて」と書いておけば、いいのだ？
8. それだけでは足りないわ。だから、操作の決まりは、LLM ではなく、ハーネスに持たせましょう。
9. ハーネスは、ツール呼び出しを動かす前に、決まりと照らし合わせるわ。
10. ファイルを読むことや、作業用のフォルダの中での書き換えは、そのまま許す決まりよ。
11. Issue への書きこみのように、外に影響する操作は、ユーザーに確認してから動かすの。
12. データベースを消すような、決まりにない操作は、断らせましょう。
13. さらに、コマンドは、OS の機能で囲った場所で動かして、触れるファイルや、つながる先をしぼるわ。
14. この囲いを、サンドボックスと呼ぶの。
15. ユーザーが確認すると、ハーネスが Issue の #128 にコメントを書きこんで、この仕事は終わるわ。

7-8 次の一語の上に（`nest`）:

1. ここで、組み立ててきたものを、外側から順に、ほどいてみましょう。
2. いちばん外側は、AI エージェントよ。
3. ハーネスが、ツールを動かしながら、LLM に、くり返し続きを書かせているわ。

7. ずんだもん: ぜんぶ、次の一語の予測の上に、組み立ててあるのだ！
8. ええ。ここまでで、LLM の仕組みと、その上にエージェントを組み立てる話は、ひととおりよ。
9. 次の章からは、いま話題になっていることを見ていくわ。まずは、長い文書を読ませると何が起きるか、からよ。

### 確認した事実と判断

1. **セッションの区切りを目的の達成に固定しない。** U5-C1はproject directoryに結び付いた保存された会話として説明し、終了後の再開・分岐を認める。U5-O1も過去のchat/sessionを継続する仕様。したがって、一つの依頼を一つのsessionで進めるのは自然な作例だが、「依頼から報告まで」が普遍的な定義ではない。複数の依頼を続けたり、一つの仕事を複数sessionへ分けたりできる。Codexの現行App Serverにある`sessionId`はlive session treeのrootを表す別の技術的用法で、動画の会話単位にそのまま対応させない（U5-O2）。
2. **ローカル保存と再開は両製品で確認できる。** Claude CodeはJSONLのtranscriptへ継続的に保存し、`claude --resume`で選べる。Codexは保存した会話を`codex resume`で開き、App Server文書にもディスク上のJSONL logがある（U5-C1/O1/O2）。Claudeには保存抑止・保持期間の設定、Codex execには`--ephemeral`がある。通常のローカル利用を説明すれば7-4.10は成立するが、全モード・全設定に必須の保存ではない。
3. **履歴から会話を再構成することと、実行環境の復元は違う。** Claudeの文書は、process終了時に動いていたtoolがresumeで完了・再実行されるわけではないと説明する（U5-C1）。一般化できる範囲は保存済み会話の続行。電源断前のshell process、外部DB、network request、ファイルの過去版まで戻るという説明にはしない。単に蓋を閉じた場合はsleepやbackground実行もあり、会話が必ず消えるとは言えない。
4. **保存ファイルとモデル入力は同じものではない。** 保存記録にはmetadata等もあり、現在のcontextはその記録に基づいて組み立てる（U5-C1/C2/O2、既存harness-facts）。「同じ文書を毎回そのまま保存」「一語ごとに同期書込み」「全履歴を常に丸ごと入力」は資料で保証されない。追加項目を記録する概念図はよい。JSONLは記録形式の一例であり、規格で共通の`session.jsonl`というファイル名が決まるわけではない。
5. **量の比率は作業次第。** contextには結果以外にも定義・指示・会話・モデル応答が含まれる（U5-C2/C3）。ログやファイルを多数読む今回の作例で結果の帯を大きくするのは自然だが、「常に多くは結果」とする実測一般則は確認できない。単一tool出力が数千tokenになり得ることは、大きい出力を明示的に扱うU5-C4とも整合する。U5-C4は10,000 token超の警告と、一定以上の結果をファイル参照へ置き換える処理を記載している。元の出力が大きくても、全量がそのまま入力されるとは限らない。
6. **読み返しには役立つが、完全な監査証跡ではない。** U5-C1のexportはmessagesとtool outputsを人が読める形にする。U5-O2にも保存履歴をresumeせず読むAPIがある。記録された呼び出し・結果から作業経過を確認できる。一方、完全な生出力の保存、改ざん耐性、外部操作の結果までの保証は原稿に足さない。保存だけでは入力長が減らない、という7-4.12は次の整理機能へつなぐ説明として正しい。
