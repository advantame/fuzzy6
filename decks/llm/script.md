# LLM の原稿

この文書は、各クリップの `script` から自動で作っています。手では直さず、クリップの `script` を直してください。dev サーバが動いている間は、クリップを直すたびに書き直されます。手で作り直すときは `npm run script -- llm` です。

話者を書いていない文は、四国めたんの文です。文の終わりの `a` などは文の id で、`compose/a` のように、クリップの id と合わせて指せます。

## 1. はじめに

### AI エージェント `opening`（19.1 秒）

1. これから、AI エージェントの話をするわ。 `a`
2. AI エージェントは、頼んだ仕事を、自分で調べたり、道具を使ったりして、最後まで進めようとする AI のことよ。 `b`
3. いまでは、さまざまな仕事で使われるようになってきたわね。 `c`
4. その中身がどうなっているのかを、土台から順番に見ていきましょう。 `d`

### 1-1 中核は LLM `core`（33.2 秒）

1. エージェントは、いくつかの部品を組み合わせて作られているの。 `a`
2. その中核にあるのが、LLM という技術よ。 `b`
3. **ずんだもん**　LLM なら、聞いたことがあるのだ。ChatGPT みたいな AI のことなのだ？ `b2`
4. おしいわね。ChatGPT のような対話型 AI サービスも、その中核に LLM を使っているの。 `b3`
5. LLM は、Large Language Model を略した名前で、日本語では、大規模言語モデルと呼ばれているわ。 `c`
6. まずは、名前の後ろ半分にある「言語モデル」から、見ていきましょう。 `g`

### 1-2 言語モデル `langmodel`（90.9 秒）

1. ここで言う「モデル」は、本物のふるまいをまねて、予測に使うものよ。 `a`
2. 天気のモデルなら、空気の動きをまねて、あしたの天気を予測するわね。 `b`
3. 言語モデルがまねるのは、言葉の並び方よ。 `c`
4. 文の中の言葉は、でたらめな順番に並んでいるわけではないの。 `d`
5. たとえば、「のどがかわいたので、水を」と来たら、次は「飲んだ」が、いちばんありそうでしょう。 `e`
6. 「買った」も、それなりにありそうね。けれど、「読んだ」は、まず来ないわ。 `e2`
7. 文法や言い回し、意味など、いくつもの決まりが重なって、ありそうな言葉と、ありそうにない言葉が分かれてくるの。 `f`
8. この決まりの重なりが、言語の構造よ。言語モデルは、これをまねて、文章に空いた穴に入る言葉を予測するわ。 `g`
9. 予測といっても、答えを一つに言い切るわけではないの。天気予報が「降水確率 70%」と言うのと、同じね。 `h`
10. 手がかりになる言葉を見て、穴に入る候補の一つ一つに、どれくらいありそうかを、数字で表すのよ。 `i`
11. この数字のことを、確率と呼ぶわ。 `i2`
12. そして、穴が書きかけの文のすぐ先にあるときは、それが「次の言葉の予測」になるの。 `j`
13. **ずんだもん**　穴埋めのことは、わかったのだ。でも、ChatGPT は、人みたいに答えて、問題まで解くのだ。 `q`
14. **ずんだもん**　あれと、この穴埋めが、つながっているのだ？ `q2`
15. ええ、つながっているわ。ChatGPT の中の LLM も、穴埋めをくり返して、答えの文章を書いているのよ。 `k`
16. 言葉の並び方には、人の知識や考えも表れているわ。実際、穴埋めを鍛えたモデルは、多くの問題で成績を上げてきたの。 `k2`

### 深掘り なぜ解けるのか `whyai`（87.9 秒）

1-2 の 14（`langmodel/q2`）から降りられる。降り口の札は「ChatGPT とつながる？」。

1. **ずんだもん**　穴埋めだけで、どうして問題まで解けるのだ？ `ask`
2. 次の言葉を当てるには、何が必要なのかを、四つの問題で確かめてみましょう。 `plan`
3. 一問め。「わたしは毎朝、学校へ」。続く言葉は、何かしら。 `p1`
4. **ずんだもん**　「行く」なのだ。 `z1`
5. そうね。これは、文法と言い回しを知っていれば当てやすいわ。 `m1`
6. 二問め。「日本でいちばん高い山は」。 `p2`
7. **ずんだもん**　富士山なのだ。 `z2`
8. こんどは、文法を知っているだけでは当てられないわ。知識が必要なの。 `m2`
9. 三問め。「りんごが 3 個。あと 4 個もらうと、ぜんぶで」。 `p3`
10. **ずんだもん**　7 個なのだ。 `z3`
11. これには、計算する力が要るわね。 `m3`
12. 最後の問題は、初めて読む推理小説の、おしまいの一行よ。「犯人は」。 `p4`
13. **ずんだもん**　……読んでみないと、見当もつかないのだ。 `z4`
14. そうよね。これを当てるには、手がかりや人の関係を、はじめから追っていくことになるわ。 `m4`
15. 次の言葉をうまく当てようとすると、文法だけでなく、知識や計算、話の筋を追う力も、ものを言ってくるの。 `s1`
16. それは、言葉の中に、人が知っていることや考えたことが、書き込まれているからよ。 `s2`
17. 実際に、次の言葉の予測だけを学んだ、大きさの違うモデルどうしを比べた研究があるの。 `s3`
18. その結果、大きいモデルほど、知識や計算、前の文脈を使う問題で、おおむね成績がよかったわ。 `s3a`
19. こうして学んだ LLM に、人の指示に沿って答える学習を重ねたものが、ChatGPT の中核になっているの。 `s3b`
20. ただ、当てられることと、わかっていることが同じかどうかは、いまも議論が続いているわ。 `s4`
21. **ずんだもん**　「当てるだけ」の中身は、深そうなのだ。 `z5`

### 1-3 文章を組み立てる `compose`（36.9 秒）

1. 穴埋めをくり返していけば、文章を組み立てることができるわ。ただ、その組み立て方は、一つではないの。 `a`
2. いま広く使われている LLM は、文章を前から順に書いていくわ。 `b`
3. 書きかけの文の後ろにある穴を埋めたら、そのすぐ先に、また新しい穴を開けるの。 `c`
4. このように、書いた部分を手がかりにして、すぐ先の穴を一つずつ埋めていくモデルを、自己回帰型モデルと呼ぶわ。 `c2`
5. 一方で、穴だらけの下書きから始めて、あちこちの穴を、何か所かずつ埋めていく作り方もあるわ。 `d`
6. これは、拡散型と呼ばれる作り方の一つよ。 `e`
7. この先は、自己回帰型 LLM のしくみを、見ていきましょう。 `f`

### 1-4 この先の道筋 `route`（34.4 秒）

1. ここで、この先の話の道筋を、ひととおり見ておきましょう。 `a`
2. 前半では、LLM のしくみを扱うわ。歴史と基本の考え方から始めて、チャットボットまで進むの。 `b`
3. 中ほどでは、LLM にツールを持たせて、エージェントを組み立てていくわ。 `c`
4. 後半では、いま話題になっていることを取り上げるの。知識の持たせ方、計算と値段、それからハーネスの鍛え方よ。 `d`
5. LLM という名前の残り半分、「大規模」が何を意味するのかは、歴史をたどる中で見えてくるわ。 `e`
6. それでは、歴史から始めましょう。次の言葉を当てるという考えは、どこから生まれたのかしら。 `f`

## 3. 基本概念

### 3-1 LLM の中 `inside`（58.9 秒）

1. ここからは、自己回帰型 LLM の中で、何が起きているのかを見ていきましょう。 `a`
2. LLM は、書きかけの文章をもとに、次に来る言葉の候補と、その確率を計算するの。 `b`
3. その中から一つを選んで、文章の後ろに足したら、足したところまでを手がかりに、また次を予測するのよ。 `c`
4. これをくり返して、文章が少しずつ書き進められていくわ。 `d`
5. 次を予測するときに LLM が読む、この文章を、コンテクストと呼ぶわ。 `d2`
6. LLM が書き足した部分も、コンテクストに加わるの。 `d3`
7. **ずんだもん**　その LLM の中では、何が起きているのだ？ `e`
8. 中をのぞくと、計算がいくつかの段階に分かれているの。 `f`
9. まず、コンテクストをトークンという単位に切って、番号にするわ。その番号を、一つずつ、数の並びに変えるの。 `g`
10. 次に、自分と、それより前のトークンを参考にして、その数の並びを書き換えていくわ。 `h`
11. 最後に、書き換えた数の並びから、次に来るトークンの確率を出すのよ。 `i`
12. この章では、この流れを、一つずつ順番にたどっていきましょう。 `j`

### 3-2 トークンに切る `tokens`（65.8 秒）

1. はじめの章では「言葉」と呼んできたけれど、LLM が実際に扱う単位は、トークンというものよ。 `a`
2. はじめの章の文を、GPT-4o の切り方で切ってみると、12 個のトークンに分かれるわ。 `b`
3. **ずんだもん**　言葉の切れ目とは、ずいぶん違うのだ。 `c`
4. この切り方では、文章によく出てくる文字の並びを、まとめて一つのトークンにしてあるの。 `d`
5. だから、「、水」のように言葉の切れ目をまたいだり、「飲んだ」のように、一つの言葉が分かれたりするのよ。 `e`
6. 英語では、よく使う単語なら、前の空白も含めて、一つのトークンになることがよくあるの。 `f`
7. トークンには、一つ一つに番号が付いているわ。 `g`
8. GPT-4o の切り方では、トークンは全部で約 20 万種類あって、この一覧のことを、語彙と呼ぶの。 `h`
9. 切り方と語彙は、モデルごとに決まっているのよ。GPT-4 の切り方だと、同じ文が 17 個のトークンになるわ。 `i`
10. こちらの語彙には、「飲」という字がないので、文字を表すもっと細かい単位で、二つに割っているの。 `j`
11. こうして細かく分ければ、語彙にない文字も、トークンの並びで表せるわ。 `k`
12. そして、LLM が実際に読んだり書いたりしているのは、この番号の並びなのよ。 `l`

### 3-3 意味を数の並びに `embedding`（70.5 秒）

1. トークンの番号は、名札のようなものよ。番号が近いからといって、意味も近いわけではないの。 `a`
2. 「犬」と「猫」は似た意味なのに、番号は、ずいぶん離れているわね。 `b`
3. そこで LLM は、大きな表を一つ持っていて、番号ごとに、決まった数の並びを取り出すの。 `c`
4. このように、トークンを数の並びで表すことを、埋め込みと呼ぶわ。数の並びは、ベクトルとも呼ぶの。 `c2`
5. ベクトルに並ぶ数の個数は、モデルによって違うわ。GPT-3 の最大のモデルでは、12,288 個の数になるの。 `d`
6. この表の数は、学習の中で決まっていくわ。すると、意味の関係が、ベクトルにも表れてくることがあるの。 `e`
7. 平面に描いたイメージで見てみると、動物は動物、食べ物は食べ物で、近くに集まるわ。 `f`
8. **ずんだもん**　ベクトルで、意味の関係まで表せるのだ？ `q`
9. 英語の単語のベクトルを調べた 2013 年の研究に、こんな計算があるの。 `h`
10. 「王」から「男」を引いて、「女」を足すと、いちばん近いのは「女王」になったのよ。 `i`
11. 言葉の関係が、ベクトルの差の向きにも表れていた、ということね。 `j`
12. ただし、ここまでのベクトルは、トークン一つぶんのものよ。前の言葉を見ないと、意味が決まらない言葉もあるわ。 `k`

### 3-4 前を見て決める `attention`（75.3 秒）

1. 「かける」という言葉は、電話をかける、眼鏡をかける、橋をかける、のように、いろいろな意味で使われるわね。 `a`
2. この三つでは、前にある言葉が、意味を見分ける手がかりになるの。 `b`
3. ここで見る LLM にも、前の言葉を参考にする、アテンションという計算があるわ。 `c`
4. トークンの一つ一つが、自分と、それより前のトークンを、どれだけ参考にするかを、数で決めるのよ。 `d`
5. たとえば「かける」は、「電話」を強く参考にするわ。 `e`
6. 参考にする度合いに応じて、それぞれの情報を、自分のベクトルに混ぜ込むの。 `e2`
7. こうして、同じ「かける」でも、前の言葉に応じて、ベクトルが変わっていくのよ。 `f`
8. **ずんだもん**　後ろにある言葉は、見ないのだ？ `g`
9. 自己回帰型 LLM では、自分より後ろのトークンは、見ないように作られているの。 `h`
10. 書いている途中では、後ろは、まだ書かれていないものね。 `h2`
11. 並び順もわかるように、トークンの位置の情報も、計算に使われているわ。 `i`
12. LLM の中では、この前を見る計算のあとに、トークンごとにベクトルを作り変える計算が続くの。 `j`
13. 大きく分けると、この二つを一組にして、何十段も重ねるわ。GPT-3 の最大のモデルでは、96 段あるのよ。 `k`
14. この形は、2017 年の Transformer で示されたものよ。いまの LLM の多くも、この考え方を受け継いでいるわ。 `l`

### 3-5 次を確率で選ぶ `predict`（64.3 秒）

1. 書き換えを重ねたベクトルのうち、いちばん後ろのトークンのものから、次のトークンを予測するの。 `a`
2. 語彙のすべてのトークンに、点数を付けるわ。GPT-4o の切り方なら、およそ 20 万種類よ。 `b`
3. その点数を、全部を足すと 100% になる確率に直すの。 `b2`
4. この例では、いくつかの候補に、高い確率が集まっているわ。残りのほとんどは、0 に近いの。 `c`
5. 選び方の一つが、確率に応じて、くじを引くように一つを選ぶ方法よ。 `d`
6. この方法なら、いつも確率のいちばん高いものが、選ばれるとは限らないわ。 `e`
7. **ずんだもん**　同じことを聞いても、答えが毎回少し変わるのは、そのためなのだ？ `f`
8. ええ、理由の一つはそれよ。選び方のばらつきは、温度と呼ばれる設定で、小さくも大きくもできるの。 `g`
9. 選んだトークンを後ろに足したら、そこまでを手がかりに、また次の一つを選ぶわ。 `h`
10. この基本の手順では、100 トークン書くなら、一つ選んで足すことを、100 回くり返すの。 `i`
11. そして、終わりを表す特別なトークンが選ばれると、それを受け取ったプログラムが、そこで書くのを止めるのよ。 `j`
12. 決めておいた長さの上限に届いたときも、そこで止まるわ。 `k`

### 3-6 予測を練習する `pretrain`（101.6 秒）

1. では、確率を出すための計算は、どうやって決まったのかしら。 `a`
2. ここまでに見た、埋め込みの表や、前を見る計算、確率を出す計算には、たくさんの数が使われているの。 `b`
3. 計算のしかたを決める、この数を、パラメータと呼ぶわ。GPT-3 の最大のモデルには、1750 億個あるのよ。 `c`
4. はじめは、多くのパラメータを、乱数で決めておくの。まだ、文章の続きを予測するようには、学んでいないわ。 `d`
5. そこで、たくさんの文章を読ませて、先を隠したまま、次のトークンを当てさせるのよ。 `e`
6. たとえば、この文では、「水を」の次に、「飲」の字が続いているわね。 `f`
7. モデルが「飲」の字に付けた確率が低いほど、外れが大きかったと考えるの。 `g`
8. いろいろな位置での外れをまとめて、それが小さくなるように、パラメータを少しずつ調整するわ。 `h`
9. どう変えると外れが減るかは、計算で求められるのよ。 `h2`
10. これを、たくさんの文章で、何度もくり返すの。学習のあいだも、先の答えは見せないようにしているわ。 `i`
11. 大量の文章でこの練習をして、モデルの土台を作る段階を、事前学習と呼ぶのよ。 `j`
12. 使われる文章の量は、2020 年の GPT-3 で 3000 億トークン、2024 年の Llama 3 では、15 兆トークンを超えたわ。 `k`
13. 2025 年には、20 兆や 36 兆トークンで学習したモデルも、公表されているの。 `k2`
14. **ずんだもん**　使っているうちに、どんどん覚えていったりはしないのだ？ `l`
15. ふつうに答えを作るあいだは、パラメータは変わらないわ。でも、会話や保存した情報を、答えの手がかりにはできるの。 `m`
16. パラメータを変える追加の学習は、また別の仕組みよ。 `m2`
17. こうして、文章の続きを予測する力が育つわ。 `n`
18. 相手の指示に沿って答える力を整えるために、さらに学習を重ねるのよ。それは、次の章で見ていきましょう。 `n2`

### 3-7 読める長さ `context`（64.6 秒）

1. コンテクストに入れられるトークンの数には、上限があるわ。 `a`
2. この範囲を、コンテクストウィンドウと呼ぶの。文章をのぞく窓のようなものね。 `b`
3. 答えを作るときは、この窓に入っている文章を、手がかりにするのよ。 `c`
4. 最初に与えた文章だけでなく、書いていく答えも、この窓の中に入っていくわ。 `d`
5. 文章が長くなると、窓に入っていない元の文章は、そのままでは参照できないの。 `e`
6. だから、どこを残し、どこを省くかを、LLM を使うプログラムの側で決めるのよ。 `f`
7. 前の内容を、短くまとめて残す方法もあるわ。 `f2`
8. 窓の大きさは、2020 年の GPT-3 では、2,048 トークンだったの。 `g`
9. 2026 年には、100 万トークン規模を扱えるモデルも、いくつもあるわ。 `h`
10. **ずんだもん**　100 万トークンって、どれくらいなのだ？ `i`
11. 青空文庫の『坊っちゃん』を、GPT-4o の切り方で数えると、約 7 万 6 千トークンになるの。 `j`
12. 100 万トークンは、その約 13 冊ぶんにあたるわ。『こころ』なら、約 8 冊ぶんね。 `j2`
13. ただ、長く読めることと、長い文章のどこでも同じようにうまく使えることは、別の話なの。 `k`

## 4. チャットボット

### 4-1 続きを書くだけ `base`（80.0 秒）

1. 事前学習を終えたモデルは、文章の続きを予測することを、たくさん学んできたわ。 `a`
2. たとえば、このモデルに、「日本の首都はどこですか？」だけをコンテクストとして与えた場面を考えてみましょう。 `b`
3. 答えではなく、「アメリカの首都はどこですか？」のように、別の質問を続けることもあるの。 `c`
4. InstructGPT の論文にも、GPT-3 が質問に、別の質問で続けた例が載っているわ。 `c2`
5. **ずんだもん**　質問したのに、答えてくれないのだ？ `d`
6. 事前学習で学んだのは、書かれた文章に、どんな続きが来るか、ということなの。 `e`
7. 質問に答える形になるとは、限らないのよ。 `e2`
8. たとえば、問題集のような並びなら、質問の次に、また質問が来ることもあるわね。 `f`
9. 逆に、コンテクストの形を整えてやると、続きも変わるわ。 `g`
10. 質問と答えの組をいくつか見せて、最後は、新しい質問と「答え：」まで書くの。 `h`
11. そうすると、答えの形で、続きを書きやすくなるわ。 `h2`
12. 2020 年の GPT-3 の論文では、質問と答えの例をコンテクストに入れて、続きを書かせる方法も試しているわ。 `i`
13. パラメータは変えずに、例を、コンテクストの中に置いただけなの。 `i2`
14. チャットボットでは、だれの発言かを、決まった印で区切る形式も使われているわ。 `j`

### 4-2 会話は一本の文書 `template`（115.1 秒）

1. チャットボットの画面では、こちらの質問と、モデルの答えが、吹き出しで交互に並んでいるわね。 `a`
2. 生成 AI を使う場面では、ユーザーが直接入力するこの文を、ふつう、プロンプトと呼ぶわ。 `a2`
3. でも、LLM にできるのは、一本につながった文書を読んで、その続きを書くことだけなの。 `b`
4. そこで、画面と LLM の間に、会話を受け渡すプログラムを置きましょう。ここでは、これをアプリと呼ぶわ。 `c`
5. アプリにまずさせるのは、会話を、一本の文書に書き直すことよ。 `c2`
6. そのままつなぐと、発言の切れ目がわからないから、発言の前に、だれの発言かを表す印を付けさせるの。 `d`
7. この例では、こちらの発言に「ユーザー」、モデルの発言に「アシスタント」の印を付けているわ。 `d2`
8. そして最後に、アシスタントの印だけを、書いておきましょう。 `e`
9. 「答え：」で終えたときと同じで、続きを書けば、それがアシスタントの発言になるわね。 `e1`
10. LLM に渡すときは、こうして整えた文書の全体が、コンテクストになるの。 `e2`
11. すると LLM は、この印に続けて、アシスタントの発言を書いていくわ。 `f`
12. でも、印も、LLM にとっては、続きとして書けるテキストの一つなの。 `g`
13. だから、このままだと、答えを書き終えた LLM は、「ユーザー」の印を書いて、次の質問まで書き続けてしまうわ。 `g1`
14. **ずんだもん**　ボクが書いていない質問が、画面に出ているのだ！ `g2`
15. そこで、答えの終わりには、終わりの印を書くように、LLM を学習させておくの。 `g3`
16. そして、アプリにこの印を見張らせて、出たところで書かせるのをやめれば、答えだけを取り出せるわ。 `g4`
17. 答え方を決めておきたいなら、アプリからの指示を、「システム」という印を付けて、頭に書いておきましょう。 `h`
18. **ずんだもん**　見えないところで、指示されていたのだ？ `i`
19. そうよ。口調や、答えるときに気をつけてほしいことを、ここで伝えるの。 `j`
20. この指示は、システムプロンプトと呼ばれているわ。これも、コンテクストの一部よ。 `j2`
21. 印の書き方は、モデルが学習で見てきた形に、そろえる必要があるの。ここで描いたのは、説明のための形よ。 `k`

### 4-3 手本で学ぶ `sft`（61.7 秒）

1. 印で会話の形を整えても、それだけで、指示に沿った答えを出せるとは限らないわ。 `a`
2. そこで、プロンプトと、望ましい答えの手本を用意するの。ここでは、人が書いた会話の手本で見てみましょう。 `b`
3. プロンプトと、それにどう答えてほしいかを示す手本が、組になっているわね。 `c`
4. これを使って、次のトークンを予測する練習を重ねるわ。手本の続きが出やすくなるように、パラメータを直すのよ。 `d`
5. ここでは、プロンプトを手がかりにして、答えの部分の予測を、手本と比べているわ。 `e`
6. こうして、アシスタントの番に、指示に沿った答えを続けるように、学んでいくのよ。 `f`
7. 手本を使うこの学習は、教師ありファインチューニング、SFT と呼ばれるわ。 `g`
8. なかでも、指示に沿う答えを学ばせるものを、指示チューニングと言うの。 `g2`
9. 2022 年の InstructGPT では、人の手本を使う学習に、約 1 万 3 千件のプロンプトを使ったわ。 `h`
10. **ずんだもん**　手本をまねるだけで、いい答えになるのだ？ `i`
11. 手本で学んだあとに、答えを比べる評価も使って、さらに整える方法があるの。次は、それを見てみましょう。 `j`

### 4-4 好みで磨く `rlhf`（60.4 秒）

1. 同じプロンプトに、モデルが書いた答えを、いくつか並べるわ。 `a`
2. 人が、指示に沿っているかなどを考えながら読み比べて、よいと思う順に並べるの。 `b`
3. この比較をたくさん集めて、人が選びそうな答えほど高い点を付ける、別のモデルを学習させるわ。 `c`
4. これが、報酬モデルよ。 `c2`
5. そして、報酬モデルの点が高くなるように、答える LLM のパラメータを調整していくわ。 `d`
6. これは、人のフィードバックを使う強化学習、RLHF の、一つのやり方なの。 `e`
7. 2022 年の InstructGPT の評価では、API の利用者から集めたプロンプトへの答えを、人に比べてもらったわ。 `f`
8. 追加の学習をした 13 億パラメータのモデルが、元の 1750 億パラメータの GPT-3 より、好まれたのよ。 `f2`
9. **ずんだもん**　大きさが百倍以上も違うのに、なのだ？ `g`
10. ええ。この実験では、大きさだけでなく、指示に沿うように追加で学習させることが、答えの評価を大きく変えたのよ。 `h`
11. 比べる学習には、比べた結果から直接調整する方法や、AI の評価を使う方法もあるわ。 `i`

### 4-5 毎回読み直す `memory`（88.0 秒）

1. チャットボットと話すときは、「二日間です」のように、相手が前の話を覚えているつもりで、返事をするわね。 `a`
2. でも、答えを作るあいだ、パラメータは変わらないし、LLM が読めるのは、渡された文書だけだったわね。 `b`
3. だから、届いた発言だけを、そのまま渡すと、LLM には、何が二日間なのか、わからないの。 `b2`
4. **ずんだもん**　何日か聞いてきたのは、そっちなのだ！ `b3`
5. そこで、アプリには、それまでのやりとりも全部つないで、毎回、頭から読ませるの。 `c`
6. 前の話が書いてあれば、LLM は、その続きとして答えを書けるわね。 `c1`
7. 3 回目も、それまでのやりとりに、新しい発言をつないで、頭から読ませるわ。 `d`
8. 同じところを毎回計算し直さないように、前の計算結果を、とっておいて使い回す工夫もあるわ。 `d2`
9. でも、こうして足し続けると、読ませる文書は、回ごとに長くなっていくの。 `e`
10. **ずんだもん**　ずっと話していたら、どうなるのだ？ `f`
11. いつかは、コンテクストウィンドウの上限を超えて、全部は読ませられなくなるわ。 `g`
12. そこで、古い部分を省かせたり、要約して短くさせたりして、ウィンドウに収めるの。 `h`
13. どう収めるかは、アプリを作る人しだいよ。収めずに、エラーで止めるアプリもあるわ。 `h2`
14. 新しい会話を始めると、文書は一から作り直すから、前の会話のことは、もう書かれていないわ。 `i`
15. そこで、覚えておきたいことを保存させておいて、次の会話の文書の頭に、書き足させましょう。 `i2`
16. すると、新しい会話でも、京都の旅行の話だとわかって答えられるわね。 `i3`
17. メモリー機能は、たとえばこうして作れるの。 `i4`

### 4-6 事実でない答え `hallucination`（59.9 秒）

1. LLM は、事実でないことを、事実と同じ調子で書くことがあるの。 `a`
2. これを、ハルシネーションと呼ぶわ。 `b`
3. たとえば、実在しない判例を、それらしい名前と年で書いてしまうことがあるのよ。 `c`
4. 文章が自然につながっていても、中身が正しいとは限らないわ。 `d`
5. 2023 年には、米国の弁護士が、AI が作った実在しない判例を、裁判所に出してしまったの。 `e`
6. 裁判所は、その後の説明も含めて、問題にしたわ。 `f`
7. 弁護士 2 人と事務所に、合わせて 5,000 ドルを支払うよう命じたのよ。 `f2`
8. **ずんだもん**　わからないなら、「わからない」と言えばいいのだ。 `g`
9. そうよね。2025 年の研究に、こんな分析があるわ。 `h`
10. 正解だけに点を付けて、「わからない」は 0 点にする評価が、当て推量を後押ししている、というものよ。 `h2`
11. 対策の一つは、資料を調べて、その内容も使って答えを作ることよ。 `i`
12. ただし、調べれば必ず正しくなる、というわけではないの。 `i2`
13. 検索などの道具を、アプリにつなぐ方法があるわ。次の章では、そのしくみを見ていきましょう。 `j`

## 5. ツール

### 5-1 ツールを使う `tools`（94.6 秒）

1. チャットボットを作っていて、ユーザーから、「あしたの京都の天気は？」と聞かれたとしましょう。 `a`
2. でも、LLM が学習で身に付けた知識だけでは、あしたの京都の最新の予報は、確かめられないわ。 `b`
3. このまま LLM に続きを書かせると、それらしい天気を、もっともらしく書いてしまうかもしれないの。 `c`
4. 一方で、天気の予報を返してくれるプログラムなら、もうあるわね。 `d`
5. でも、LLM にできるのは、文章の続きを書くことだけよ。プログラムを動かすには、別の仕組みが要るわ。 `e`
6. そこで、プログラムを動かす役は、アプリに任せましょう。 `f`
7. LLM には、答えの代わりに、「あしたの京都の天気予報を調べたい」という、アプリへのリクエストを書かせるのよ。 `g`
8. アプリは、そのリクエストを読んで天気のプログラムを動かし、返ってきた予報を、文書に書き足すわ。 `h`
9. アプリが、予報を書き足した文書を、もう一度 LLM に読ませれば、LLM は、予報を手がかりにして、答えを書けるわね。 `i`
10. **ずんだもん**　LLM が、自分で調べに行ったわけじゃないのだ？ `j`
11. ええ。LLM は、アプリへのリクエストを書いただけで、プログラムを動かしたのは、アプリよ。 `k`
12. こうして、LLM がリクエストを書けば使えるように、アプリにつないだプログラムを、ツールと呼ぶわ。 `l`
13. そして、ツールを使うために LLM がアプリに書くリクエストを、ツール呼び出しと呼ぶの。 `m`
14. アプリから動かせるようにつなげば、いろいろなプログラムを、ツールにできるわ。 `n`
15. 天気のほかにも、検索、計算機、コマンドを打つシェルなどがあるわね。 `o`
16. この章では、ツールを一回使うときの、アプリと LLM のやりとりを、順に細かく見ていきましょう。 `p`

### 5-2 ツールの定義 `toolspec`（76.3 秒）

1. LLM にツール呼び出しを書かせるには、まだ足りないものがあるの。 `a`
2. このアプリにどんなツールがあって、それぞれをどんな入力で呼び出せばいいのかは、LLM が学習で身に付けた知識からは、わからないわ。 `b`
3. そこで、アプリには、使えるツールの説明を、コンテクストに入れさせましょう。 `c`
4. 説明には、ツールの名前と、何をするのか、どんな入力を受け取るのかを書くわ。 `d`
5. こうして一つのツールを説明したものを、ツールの定義と呼ぶの。 `e`
6. この例では、アプリを作る人が、定義を、決まった形のデータで用意するわ。 `f`
7. LLM に渡すときには、アプリが、そのデータを、モデルが学習で見てきた形式のテキストに直して、コンテクストに入れるのよ。 `g`
8. 天気のほかに、検索や計算のツールも並べておけば、LLM は、ユーザーの質問に合うツールを選んで、ツール呼び出しを書けるわね。 `h`
9. **ずんだもん**　ツールの中のプログラムは、LLM には見えないのだ？ `i`
10. 定義を渡しただけでは、中のプログラムまでは見えないわ。LLM がツールを選ぶときの手がかりは、定義に書かれた説明よ。 `j`
11. だから、アプリを作る人は、何をするツールで、どんなときに使うのかを、定義にわかりやすく書いておくことが大切ね。 `k`
12. 定義もコンテクストの一部だから、一度に渡す定義を増やすほど、読ませる文書も長くなるわ。 `l`

### 5-3 呼び出しを書く `toolcall`（103.9 秒）

1. 次は、ツール呼び出しを、どんな形で書かせるかを決めましょう。 `a`
2. もし、ツール呼び出しを、ふつうの文章で書かせたら、どうなるかしら。 `b`
3. アプリには、LLM が書いたものが、ユーザーへの答えなのか、ツール呼び出しなのか、区別しにくくなるわね。 `c`
4. ツール呼び出しだとわかっても、どのツールに、何を入力として渡せばいいのかを、自由な文章から読み取るのは、大変ね。 `d`
5. そこで、ツール呼び出しを書くときの形式を、決めておくの。 `e`
6. この図の形式では、呼び出しの始まりと終わりに印を書いて、その間に、ツールの名前と入力を書くわ。 `f`
7. その中身は、アプリが読み取りやすい、JSON という形式よ。 `g`
8. モデルを作る側は、この形式でツール呼び出しを書けるように、LLM を学習させておくわ。 `h`
9. LLM は、ツール呼び出しも、ふつうの文章と同じように、次のトークンを一つずつ選んで書いていくの。 `i`
10. まず始まりの印を書き、続けて、ツールの名前と入力を、トークンごとに書いていくわ。 `j`
11. LLM が終わりの印を書いたところで、アプリが LLM に書かせるのを止めれば、ツールの名前と入力を、そのまま受け取れるわね。 `k`
12. 4 章で、答えの終わりの印で止めたのと、同じやり方よ。 `k2`
13. Anthropic の API は、ツール呼び出しで止まったことを、tool\_use という値で、アプリに知らせてくれるわ。 `l`
14. **ずんだもん**　LLM がツール呼び出しを書いたら、それだけでツールが動くのだ？ `m`
15. いいえ。ツールを動かすのは、LLM の外にあるアプリよ。 `n`
16. 自動で動かすか、ユーザーに確認してから動かすかも、アプリを作る人が決めておくの。 `n2`
17. 印や名前の書き方は、モデルによって違うわ。右上は、gpt-oss というモデルの形式に合わせた例よ。 `o`
18. この形式では、ツールの名前を宛先に、入力を本文に書くの。 `o2`

### 5-4 結果を書き足す `toolresult`（65.2 秒）

1. アプリは、受け取ったツールの名前と入力で、そのツールを動かすわ。 `a`
2. でも、ツールから返ってきた結果は、アプリの手元にあるだけで、LLM からは見えないの。 `b`
3. そこで、アプリには、結果に「ツールの結果」の印を付けて、文書に書き足させましょう。 `c`
4. どのツール呼び出しへの結果なのかも、わかるようにしておくわ。 `c2`
5. そして、LLM が続きを書けるように、アシスタントの印を、また書いておくの。 `d`
6. アプリは、結果を書き足したこの文書を、もう一度 LLM に読ませるわ。 `e`
7. すると LLM は、予報を手がかりにして、その続きに、答えを書いていくわね。 `f`
8. 答えを書き終えたら、こんどは、答えの終わりの印を書くの。 `g`
9. アプリには、LLM が何の印で止まったのかを見て、次にすることを選ばせましょう。 `h`
10. ツール呼び出しを書き終えて止まったら、ツールを動かす。答えを書き終えて止まったら、答えをユーザーに返して終えるわ。 `i`
11. **ずんだもん**　ツール呼び出しや結果は、チャットの画面には出ないのだ？ `j`
12. 出すかどうかも、アプリを作る人が決めるわ。ツールを使っている途中のようすを、画面に出すアプリもあるの。 `k`

### 5-5 答えるまで回す `toolloop`（102.3 秒）

1. こんどは、ユーザーから、「あしたの京都が雨なら、屋内で楽しめる所を教えて」と聞かれたとしましょう。 `a`
2. これに答えるには、まず天気を調べて、雨なら、屋内の場所も検索することになるわね。 `b`
3. LLM が次にどんなツール呼び出しを書くかは、その前に返ってきた結果によって変わるの。 `c`
4. そこで、アプリの動きを、くり返しの形に書いておきましょう。 `d`
5. アプリは、LLM に文書を読ませて、ツール呼び出しで止まったら、ツールを動かして結果を書き足し、また LLM に読ませるわ。 `e`
6. LLM が答えを書き終えたら、くり返しを抜けるのよ。 `f`
7. 一周めでは、LLM が、天気予報を調べるツール呼び出しを書いて、雨の予報が返ってくるわ。 `g`
8. 二周めでは、その予報を読んだ LLM が、屋内の見どころを検索するツール呼び出しを書くの。 `h`
9. 三周めで、LLM が二つの結果をもとに答えを書いて、終わるわ。 `i`
10. 晴れの予報なら、二周めで、検索せずに答えを書いて終わるわね。 `j`
11. **ずんだもん**　何回まわるかは、だれが決めているのだ？ `k`
12. 回る回数は、LLM が次のツール呼び出しを書くか、答えを書き終えるかで決まるわ。アプリは、それを見て、次の周へ進むかどうかを決めるの。 `l`
13. ただ、いつまでも終わらないと困るから、アプリを作る人が、回る回数に、上限を付けておくこともできるわ。 `m`
14. OpenAI は 2023 年に、ツール呼び出しにあたる機能を、関数呼び出しという名前で API に加えたわ。 `n`
15. Anthropic も 2024 年に、LLM にツールを使わせる API の機能を、一般に提供したの。 `n2`
16. 次の章では、この図のツールの場所に、いろいろなプログラムをつないでいきましょう。 `o`

## 6. つなぐ先

### 6-1 調べてから答える `rag`（83.9 秒）

1. 会社の中で、社内の決まりについての質問に答える、社員向けのチャットボットを作るとしましょう。 `a`
2. 社員から「出張の日当はいくら？」と聞かれたら、どうなるかしら。 `b`
3. その会社の規程が、LLM の学習に使われていなければ、LLM は、学習した知識だけでは答えられないわ。 `b2`
4. このままだと、よくある金額を、もっともらしく答えてしまうかもしれないの。 `c`
5. そこで、LLM に答えを書かせる前に、アプリに、社内の資料を検索させましょう。 `d`
6. アプリは、資料の中から、質問の答えに関係しそうな文章を、いくつか探し出すわ。 `e`
7. その方法の一つが、検索用のモデルで、質問と資料の文章をベクトルに変えて、近さを比べるやり方よ。 `f`
8. アプリが、見つかった文章を、質問と一緒に文書に書き足してから、LLM に答えを書かせるのよ。 `g`

13. **ずんだもん**　資料が見つかれば、もう間違えないのだ？ `k`

### 6-2 検索もツールに `search`（85.8 秒）

2. アプリが質問の文のまま検索すると、日当の規程は見つかっても、改定のお知らせは見つからないかもしれないわ。 `b`

4. そこで、検索を、ツールの一つにしましょう。 `d`

### 6-3 コマンドを打つ `shell`（107.4 秒）

1. コンピュータで使うプログラムには、ファイルを探すものや、計算するものなど、いろいろあるわ。 `a`

3. そこで、シェルを、一つのツールとしてつなぎましょう。 `c`

15. **ずんだもん**　いろいろなプログラムを動かせるなら、危なくないのだ？ `j`

### 6-4 自分で動く `agent`（92.6 秒）

1. こんどは、ユーザーが「ログを調べて、エラーが多い日と、その中身を教えて」と頼んだとしましょう。どう調べるかの細かな手順は、LLM に任せるわ。 `a`
2. シェルをツールとして使える LLM は、まず、日ごとのエラーの数を数えるコマンドを、ツール呼び出しに書くわ。 `b`
3. LLM が、返ってきた結果を読むと、10 月 7 日だけが、飛び抜けて多いわね。 `c`
4. そこで LLM が次に書くのは、その日のエラーの中身を見るコマンドよ。 `d`

6. ただ、途中でユーザーに確認したり、アプリが決めた回数の上限で止まったりすることもあるわ。 `e2`

11. **ずんだもん**　はじめに見たエージェントの中身は、これだったのだ！ `i`
12. ええ。次の行動を選ぶ LLM と、ツールの実行や結果の受け渡しを受け持つアプリと、ツールの組み合わせよ。 `j`

### 6-5 コードを直す `coding`（88.7 秒）

2. ここでは、ユーザーが「テストが通るように直して」と頼んだとして、エージェントが、まずテストを動かすところから、見てみましょう。 `b`

10. **ずんだもん**　テストがなかったら、どうするのだ？ `g`
11. そのときは、ユーザーがどう動いてほしいかをもとに、確かめるためのテストを、エージェントに先に書かせることもあるわ。 `h`
12. 2023 年に公開された SWE-bench は、12 の Python のプロジェクトから作った試験よ。 `i`

### 6-6 画面を操作する `gui`（130.7 秒）

18. **ずんだもん**　ボクのパソコンを、勝手に操作されたら困るのだ。 `k`

## 7. ハーネス

### 7-1 LLM の周り `harness`（94.3 秒）

1. 6 章では、LLM にツールをつないで、AI エージェントを組み立てたわね。 `a`
2. そのあいだ、アプリには、いろいろな仕事をさせてきたわ。 `b`
3. まず、会話とツールの定義を、LLM に読ませる一本の文書にまとめること。 `c`
4. LLM がツール呼び出しを書いたら、ツールを動かして、結果を文書に書き足すこと。 `d`
5. LLM がユーザーへの返事を書くまで、それをくり返すこと。 `e`
6. そして、確認が要ると決めた操作の前に、ユーザーに確認すること。 `f`
7. このように、LLM の周りで、文書を組み立て、ツールを動かし、くり返しを回すプログラムを、ハーネスと呼ぶわ。 `g`
8. **ずんだもん**　アプリとは、別のものなのだ？ `h`
9. この図のアプリと、同じものよ。名前を、エージェントの話でよく使う呼び方に替えたの。 `i`
10. Anthropic や OpenAI も、LLM に読ませる文書を整え、ツールを動かし、くり返しを回す部分を、ハーネスと呼んでいるわ。 `i2`
11. 同じ LLM でも、ハーネスの作りしだいで、できることも、試験の点も変わるわ。くわしくは、10 章で見ていきましょう。 `j`
12. ここで、6 章でエージェントがログを調べた話に戻るわ。 `k`
13. 10 月 7 日のエラーの多くは、データベースの時間切れだったけれど、その理由は、まだわかっていなかったわね。 `l`
14. そこで、ユーザーが「時間切れの原因を突き止めて、直す変更を作って。わかったことは、GitHub の Issue に書いておいて」と頼んだとしましょう。 `m`
15. **ずんだもん**　調べて、直して、書きこんで。長い仕事になりそうなのだ。 `n`
16. この仕事を進めながら、ハーネスに足していく仕事を、一つずつ見ていくわ。 `o`

### 7-2 共通の差し込み口 `mcp`（95.4 秒）

1. Issue は、直したい問題や、これからする仕事を書きこんで、チームで追いかけるための場所よ。 `a`
2. 同じ時間切れのことを、もうだれかが書きこんでいるかもしれないわね。 `b`
3. GitHub には、ほかのプログラムからIssue を読み書きするためのAPI があるわ。 `c`
4. その API を呼ぶプログラムをハーネスに組みこめば、ツールとして使えるの。 `d`
5. でも、つなぎたいサービスは、GitHub だけではないわ。 `e`
6. ハーネスのほうも、ターミナルで使うもの、エディタで使うもの、と一つではないわね。 `f`
7. 三つのハーネスと四つのサービスを、組ごとに専用のプログラムでつなぐなら、3 かける 4 で、12 本を書くことになるわ。 `g`
8. そこで、ハーネスと、サービスにつなぐプログラムとのやりとりを、共通の形にそろえましょう。 `h`
9. 使えるツールを尋ねる、ツールを呼ぶ、といったやりとりを、どのハーネスも、同じ形で送るの。 `i`
10. サービスごとに、この形でやりとりするプログラムを一つ用意すれば、どのハーネスでも使い回せるわ。 `j`
11. 用意するプログラムは、ハーネスの側に三つ、サービスの側に四つ。3 たす 4 で、7 本になるわね。 `k`
12. この決まりを、MCP と呼ぶわ。Model Context Protocolの略よ。 `l`
13. ハーネスからの問い合わせや呼び出しに答えるプログラムを、MCP サーバーと呼ぶわ。 `m`
14. 手元のパソコンで動かすものも、ネットの先で動くものもあるの。 `m2`
15. MCP は、2024 年 11 月に Anthropic が公開し、2025 年 12 月には、Linux Foundationのもとの団体に寄贈されたわ。 `n`
16. **ずんだもん**　差しこみ口の形を、そろえたってことなのだ？ `o`
17. そうよ。MCP に対応したハーネスなら、同じ MCP サーバーを使い回せるわ。 `p`

### 7-3 定義を取り寄せる `mcpflow`（85.7 秒）

6. LLM は、その定義を読んで、Issue を検索するツール呼び出しを書くの。 `f`
7. ハーネスは、その呼び出しを、MCP の形に直して、サーバーに送るわ。 `g`
8. サーバーは、GitHub の API を呼んで、見つかった Issue を返してくれるわね。 `h`
9. ハーネスは、それを、ツールの結果として、文書に書き足すわ。 `i`
10. **ずんだもん**　LLM は、MCP のことを知らなくても、いいのだ？ `j`
11. ええ。LLM に書かせるのは、5 章と同じツール呼び出しで、MCP の形で書かせる必要はないわ。 `k`
12. MCP でやりとりするのは、ハーネスとサーバーなの。 `l`

15. そこで、ツールを探すツールを用意して、LLM に、要るツールを探させてから、その定義を読ませる仕組みもあるの。 `o`

### 7-4 記録を残す `session`（78.7 秒）

1. ここから、エージェントは、ログやコードを読み、コマンドを試しながら、原因を探していくわ。 `a`
